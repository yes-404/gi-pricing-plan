  §7) — a Golden Quote's `expected.payable_premium_minor` and a property assertion's
  `payable_premium_minor > 0` are both already written this way in `03` §4.7's example and
  nothing in this plan changes that.
- `pricing-core` stays importable standalone with zero FastAPI/SQLAlchemy/Redis dependencies
  (`CLAUDE.md` §2) — the regression-run executor calls `pricing_core.rating.score_one`
  exactly as W11's evaluator does; it does not import backend infrastructure into
  `pricing-core`, and it does not import `pricing-core` into a route handler without going
  through the same seam W11 Task 1.4 built.
- Nobody hand-writes a shape `model-schema` already owns (`CLAUDE.md` §2) — a `RegressionRun`
  row is generated-contract-shaped where one exists; §5.2's slice work is what decides
  whether it becomes a `model-schema` artifact or stays hand-authored the way `score_batch`'s
  frame contract (`03` §4.8) does, and that decision belongs to the slice that builds it, not
  to Slice 1.
- The gate-coverage cluster (`F27(c)`, `F29`, `F33`, `docs/audit/plan-reviews.md` DP-1) is
  **explicitly out of scope for this Work** — the lead's ruling, `docs/audit/
  plan-reviews.md` Plan review 11. `GOLDEN_QUOTE_MISMATCH`'s registration (Slice 1 Task 1.3)
  is the one instance of that cluster's shape inside W12's own scope and is handled directly;
  no general spec-vs-code comparison mechanism is built by this plan.
- Every plan cites its FR-/NFR- ids individually, never as a bare numeric range

## Decision points — unruled; named here because nowhere else names them

**DP1 — who builds `FR-RATE-45` (the Quote Sandbox), and where does its backend endpoint
live?** `docs/roadmap.md:377`'s W12 row carries `FR-RATE-45` in its id range without naming it
in its three-item charter text ("golden quotes, property assertions, regression runs"), and
`docs/roadmap.md:381`'s W15 row separately claims "quote sandbox + ladder waterfall" as a
**frontend** deliverable. `docs/specs/03-rating-engine.md:597` cites `POST /api/v1/score/
compare` against `FR-RATE-45`, and plan review 10's own endpoint enumeration
(`docs/audit/plan-reviews.md:2352`) listed that route with no workstream attribution at all —
the one route in its list left unattributed, which this plan reads as evidence the ambiguity
is real rather than an oversight in that review.

- **Option A — split by layer.** W12 builds the backend route (`POST /api/v1/score/
  compare`, the step-level diff `pricing-core` can already produce from two `score_one` calls
  against two `CompiledBundle`s); W15 builds the frontend Quote Sandbox view on top of it,
  consistent with every other W12/W15 pairing (W12 is backend testing infrastructure, W15 is
  the frontend layer over the whole of Phase 2). **Recommended**: it is the reading every
  other route in Phase 2 already follows, and it resolves the double-homing without moving
  either row's other content.
- **Option B — hold `FR-RATE-45` for W15 entirely,** since the roadmap's charter text (not
  its id range) is what a reader would follow, and the sandbox's value is the frontend
  comparison view, not the route in isolation. Costs: W15 would then need `pricing-core`
  scoring knowledge W12's own regression-run work builds first, so W15 either duplicates it
  or takes a dependency on W12 finishing — the DP3-style latency-harness dependency review 8
  already flagged as a real cost when a boundary bends.
- **Option C — correct the roadmap row to drop `FR-RATE-45` from W12's range and leave a
  cross-reference**, formalising Option A's split without W12 building any of it. Costs: the
  comparison endpoint then has no owning Work until W15 opens, and W15's own row does not
  currently name a backend task, only "quote sandbox."

This plan proceeds on **Option A** for sequencing purposes (Slice 4 below is scoped to the
backend route only), but does not treat that choice as ruled — Slice 4 does not open without
a dated decision, and Slices 2–3 do not depend on which option is chosen.
