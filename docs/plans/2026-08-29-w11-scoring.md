  Slice 1's own tests cannot create a *real* (non-seed) Rating Version to compile and score

  its first slice"** (`...rulings.md:87-88`) — not a lesser, adjacent concern; an earlier

  `reference_table`, `custom_objective`) raises `NOT_FOUND` citing a comment that predates
  W10's real rate-table storage. `compile_rating_version` (`:283-288`) persists only

  payloads; nothing loads a bundle back. The rulings record introduces the resolver content

  (`...rulings.md:339-345`). An earlier draft of this plan split the two into separate
  numbered prerequisites, which is the over-split the dated correction below records.
  **Discharged by:** Task 1.2 — its own two-part defect description keeps both halves
  visible even though the rulings record counts them as one.
- **`CompiledBundle` — the type every `score_one`/`score_batch`/`dislocate`/
  `run_regression` signature in `03` §5.2 takes — has no code definition anywhere.** The
  only real class is `Bundle` (`pricing_core/rating/compile.py:350`), the serialised,
  hashable *record*. Ruled: `CompiledBundle` is a distinct, new *loaded* runtime wrapper —
  an initialised engine handle plus hydrated boosters — never itself serialised (Ruling 4,
  `...rulings.md:256-338`). **Discharged by:** Task 1.3.
- **`to_jdm()` does not produce the shape the engine's Python binding actually consumes —
  found from a different document than the other three, after this plan's first commit.**
  `pricing_core.rating.compile.to_jdm` (`compile.py:325-347`) and the `JdmGraph` it returns
  (`compile.py:308-322`) both claim, in their own docstrings, to produce "the engine's graph
  shape" — but `docs/research/zen-evaluate-concurrency.md:147-153` (merged, `0b218f3`, PR
  #321) found otherwise while building a graph to measure against: the spike built its JDM
  by hand, directly against `gorules/zen`'s own `test-data/expression.json` fixture,
  "**not** through `pricing_core.rating.compile.to_jdm`, which produces an intermediate
  shape for pricing-core's own use and is not what the engine's Python binding actually
  consumes; that further translation does not exist yet"
  (`...zen-evaluate-concurrency.md:151-153`). **Trust the measurement, not the docstring**:
  nothing in this codebase has ever fed a `to_jdm()` output to a live engine handle and
  gotten a result back. Unlike the other three, this needs no ruling — its target shape is
  fixed externally by `gorules/zen`'s own wire format, not an internal design choice, so
  there is nothing for a decision-maker to decide, only something to build. **Discharged
  by:** Task 1.3 — `load_bundle` cannot produce a working `CompiledBundle` without this
  translation existing somewhere on the path from `Bundle.graph` to the engine handle;
  whether that lands as a rewritten `to_jdm`, a second function composed after it, or logic
  inline in `load_bundle` is this task's own design choice, exactly as Ruling 4 already left
  `CompiledBundle`'s field shape open.

### 1.3 — `CompiledBundle`: the loaded runtime wrapper (Ruling 4)

**The defect, in two parts found from two different documents, that land together because
neither is useful without the other.** (a) Every `03` §5.2 scoring signature takes

the spec's name, as a **distinct** type from `Bundle` (`compile.py:350`) — `Bundle` stays
the self-contained, cacheable, distributable *record*; `CompiledBundle` is what a warm
worker process holds after loading one (Ruling 4). (b) Even with `CompiledBundle` built,

(`compile.py:325-347`) produces an intermediate shape for pricing-core's own use, not what

plain engineering gap needing no ruling, since the target shape is fixed externally by
`gorules/zen`'s own wire format, not by an internal design choice.

**Files**
- Create: `packages/pricing-core/src/pricing_core/rating/runtime.py` — the `CompiledBundle`

  against a docstring's claim. Exact field shape of `CompiledBundle` itself, and of this
  translation, is this task's own design, constrained only by what Task 1.4's evaluator
  needs to call — per the ruling's own words, "not fixed here."
- Modify: `packages/pricing-core/src/pricing_core/rating/compile.py`'s `to_jdm`/`JdmGraph`
  docstrings — both currently claim, unqualified, to produce "the engine's graph shape,"

### 1.4 — The evaluator: `score_one` on `async_evaluate()` (Ruling 5)

**The design, already ruled, not open.** `score_one`'s real-time path is built directly on
the ZEN engine's `async_evaluate()` binding, never `evaluate()` plus `run_in_executor`
thread-pool offload — measured twice on this machine (`docs/research/zen-evaluate-
concurrency.md`): sync `evaluate()` blocks the event loop completely (a 1 ms heartbeat got
zero ticks during one call); thread-offloaded `evaluate()` is *worse than sequential*
(0.90–0.93x); `async_evaluate()` is both non-blocking and delivers real throughput
(2.10–2.25x on 4 cores). `03-rating-engine.md:598`'s `score_one` signature is already
corrected to `async def` in this commit's predecessor.

**Files**
- Create: `packages/pricing-core/src/pricing_core/rating/score.py` — `async def
  score_one(bundle: CompiledBundle, ctx: QuoteContext, *, trace: bool = False) ->
  ScoringResult`, calling `CompiledBundle`'s engine handle's `async_evaluate()`. Implements:
  every step type's evaluation (table lookup, expression, `model_call` delegating to
  `predict_gbm`/`predict_glm` with `nthread=1`, constraint decline), the premium ladder via
  `pricing_core.money.apply_factor`/`reconcile_ladder`, the `purpose`-conditional sub-graph
