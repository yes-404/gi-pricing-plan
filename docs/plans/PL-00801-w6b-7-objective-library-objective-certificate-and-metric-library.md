# W6b-7 — Objective library, objective certificate, and metric library

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the three `02` §5.3 views that read the custom-artifact libraries —
`/objectives`, `/objectives/:id/certificate` and `/metrics` — against APIs that are already
built, and discharge the FR-24 carve-out that falls due at this plan.

**Architecture:** Three routed views over two API modules. The two library views are the same
table twice: `02` §5.3 calls the metric library "the mirror of the objective library above",
and the two backends are structurally identical (seven routes against eight, differing only by
`/derive`), so the list surface is one component parameterised by its artifact, not two
components that will drift. The certificate view is its own screen because it renders a
different shape — nine named checks with a four-value status — and because it carries the one
presentation obligation this slice is required to write down.

**Tech Stack:** Vue 3 `<script setup lang="ts">`, vue-router 5.2.0 function-mode props, Pinia
not required (no cross-view state), Tailwind, Vitest. Types come from
`frontend/src/api/generated/schema` via `components["schemas"][…]` and are never hand-written.

**Spec:** [`../specs/02-modelling.md`](../specs/02-modelling.md) §3, §4.7, §5.1 and §5.3;
[`../specs/00-overview.md`](../specs/00-overview.md) FR-24.

## Global Constraints

- **Never hand-write an API type.** Every shape is `components["schemas"][…]`.
  `frontend/src/api/generated/` is VCS-ignored: it is generated by
  `pnpm --dir frontend generate:api` and may not be cited as evidence.
- **Vue 3 Composition API with `<script setup lang="ts">` only.** No Options API, no JSX.
- **Both halves of the gate must pass locally before pushing** — `CLAUDE.md` §11. A
  Python-only "gate" has been green here while the frontend was red.
- **A `02` §5.3 Contents cell binds nothing** (FR-24), except the seven carve-outs it
  names. Anything a view needs beyond the generated contract is a **new requirement raised at
  build time** (OQ-587's floor rule, decided 2026-08-21), brought to the manager, never a
  silent addition.
- **FR-24 is not a licence to drop an item.** A view is an obligation because it has a **row**
  in a §5.3 table — `02`:2647 states this directly, and forty-seven of the fifty-one
  registered views have no FR at all. FR-24 decides whether a *listed affordance* binds; it
  never decides whether the row does. Every item in a cell this slice touches therefore gets one
  of `CLAUDE.md` §13's four verdicts with an owner, and none is left unmentioned.
- **Requirement ids are permanent** (`CLAUDE.md` §5). This plan **takes no new id**; there is
  no `Next free:` marker. Highest ids in use at `origin/main` `65b2e10`: FR-168,
  NFR-488, OQ-610.

## Four findings, resolved here rather than inherited

### Finding 1 — `02` carries two different route strings for the certificate view

`02` §5.3:2593 registers `/objectives/{id}/certificate`. The "Not built, 2026-08-18" note at
`02`:2655-2656 names `/objectives/:slug@:version/certificate`. They cannot both be the route.

**This slice does not decide it. It was decided on 2026-08-23, and the decision is `{id}`.**
`02`:2630-2637 — *"Three route cells in this table addressed an artifact as `:slug@:version`:
Diagnostics, Objective certificate and Peril structure. **The spec was the wrong side.**"* It
rules that Diagnostics keeps `:slug` with `?version=` while *"the other two take the id their
routes actually serve"*. §5.3:2593 already carries that outcome. **The plan's job is to cite
that ruling, not to re-take it** — a plan that re-derives a decided question produces a second
answer that can disagree with the first.

**What is actually broken is one stranded list-mate.** The 2026-08-23 amendment moved the three
*route cells* and left the 2026-08-18 prose note quoting the old string. The control that shows
this is a strand and not a blanket miss: the Diagnostics cell **correctly did not** move to
`{id}` — it kept `:slug` with `?version=` — so the amendment discriminated between its members
and simply did not sweep prose. A repository-wide check confirms the strand is exactly one:

```bash
git grep -n "slug@:version" -- docs
```

Two hits on `origin/main` `65b2e10` — `02`:2631, which quotes the string in order to retire it,
and `02`:2656, which still uses it. Task 1 fixes the second and leaves the first.

**The third route form, named and closed.** `/objectives/:slug/v/:version/certificate` is
*representable* — `CustomObjective` carries both `slug` and `version`, and
`frontend/src/router/index.ts`:35 already routes `/data/:slug/v/:version` — so the `@` argument
alone does not close it. **What closes it is that no §5.1 objectives route resolves a
slug-and-version pair.** All eight are `/api/v1/custom-objectives/{id}…` (§5.1:1721-1728); the
list's `slug` filter is exact-match and returns versions, so such a view would have to
synthesise the resolution from a list sweep on every load. The spec says this itself, in the
same 2026-08-23 amendment: *"What id addressing cannot express is a governance deep link —
'the certificate as it stood at version 3' needs a read arm that resolves `(slug, version)`,
and there is none. That is a read to add when the governance UI needs it (Phase 3)."*

**Where the `@` came from, since it is worth not repeating.** `custom_objective:<slug>@<version>`
is this platform's **reference string** — a governance address resolved by the `slug` filter
(`backend/src/app/db/models.py`:1604, `platform/objectives.py`:403). It was never a URL, and the
§5.3 cells transcribed it into one. The independent reason not to put an `@` in a path is
recorded at `frontend/src/router/index.ts`:106-108: *"an `@` must be percent-encoded by every
client, and `family@7` then reads as `family%407` in every log and support conversation."* Cite
that comment, not the API shape — `/api/v1/…` is a different namespace and proves nothing about
what a frontend route may look like.

Task 1 appends a dated line to the note rather than rewriting it — `CLAUDE.md` §5, the same
treatment FR-166's superseded point *(a)* received on 2026-08-24.

### Finding 2 — `/metrics` sits in no slice row

register a metric-certificate route. Building one would be building a view the spec has not
declared. The cell's other two items — the editor and the certificate link — are booked as
deferred with owners in the item-by-item table below, not dropped. See finding 4.

**A latent path collision, recorded not fixed.** `backend/src/app/api/health.py`:137 serves
`GET /metrics` — Prometheus, unauthenticated, FR-443. The SPA route `/metrics` and that
endpoint collide only under same-origin serving, which does not exist today (the frontend is a
Vite dev server and the API is mounted under `/api/v1`). It is real and it is latent; Task 5
records it in the router beside the route, and the roadmap proposal below hands the deployment
question to its owner. **Do not rename either one in this slice** — renaming the Prometheus
path breaks a scrape config to fix a collision that has not happened.

### Finding 3 — FR-24's carve-out 4 falls due at this plan

Not a finding this slice may choose to take. FR-24 (`00-overview.md`:227) makes every §5.3
Contents cell prose that binds nothing **except seven named cells**, each of which "carries an
obligation held in no requirement and no contract and so **remains binding until it is
discharged**". The fourth is *"`02` Objective certificate's `violated`-as-a-finding presentation
rule"*, and the rule states: *"**Each discharge is owned by the slice that builds the view
carrying it, and falls due at that slice's plan**"*. This slice builds that view; this is that
plan.

FR-24 names FR-152 as one of two carve-outs whose cited requirement does not carry its
obligation, and says a discharge is *"checked by reading the cited requirement's predicate, not
by confirming its id exists"*. Read at `02`:216, FR-152 obliges three things — the
`convexity: violated` flag, a declared hessian clipping strategy (`clip_to_min`, `abs`,
`gauss_newton`), and an additional Approver. **No presentation obligation.** FR-24 is
correct.

**Resolved: discharge by extending FR-152, not by declaring the cell exhaustive and not by
raising a new id.**

*Why not exhaustive.* A declared-exhaustive cell binds its whole list, and this cell names a
*"convexity heatmap over the sampled `(y, f)` domain"* that the contract cannot supply at any
depth: `CertificateCheck` is `name`/`status`/`detail`, and `SamplingSpec` carries `n_points`,
`seed`, `y_range`, `f_range`, `w_range` — grid parameters, never per-point hessians. Declaring
the cell exhaustive would therefore bind an artifact that, under OQ-587's floor rule, is
itself a new requirement. It is the more expensive discharge, and it does not put the
presentation rule anywhere a reader of the requirements will find it.

*Why extend 43 rather than mint a new id.* FR-152 already carries the same rule one level
down. Its text says a non-convex objective *"is not refused outright"* — that is the
**non-blocking** rule at the level of the verdict, and `CertificateResult.outcome_of`
(`packages/model-schema/src/model_schema/objectives.py`:710-716) is where it is computed:
`certified_with_findings`, not `failed`. What no requirement holds is the same rule one level
up, at the **surface**: nothing says a view may not take that non-blocking verdict and render
the `violated` row as a failure anyway. Extending 43 puts the two levels of one rule in one
place. A new frontend-only id would split them, and would leave §5.3's citation of FR-152
pointing at a requirement that still did not carry what the cell claims. The precedent is
FR-187, whose dated amendment blockquote sits directly below its row in the same table.

**No `CLAUDE.md` §0 gap in `outcome_of`, and an earlier draft of this plan was wrong to claim
one.** The claim was that its docstring attributes a presentation rule to FR-152 and reads
narrower than its own code. Both halves fail on reading the artifacts. The docstring's general
sentence — *"Any `warn` or `violated` is a finding"* — is unqualified and matches the code
exactly; FR-152 is then cited as the **instance** that motivates it, not as its scope. And
the clause attributed to 43, *"not something that blocks"*, is 43's own *"is not refused
outright"*. `outcome_of` derives a status and presents nothing, so it was never the site of a
presentation obligation. The render rule is the sole unheld obligation, and it is the only thing
the amendment adds.

**The extension must bind a surface, not a status derivation.** This is the bar the amendment
has to clear, and it is what makes the discharge real rather than an id that exists: FR-24
warns that a discharge is *"checked by reading the cited requirement's predicate, not by
confirming its id exists"*, so an extension that merely restated `outcome_of`'s mapping would
sweep green while changing nothing. The test of whether the text below clears it: **a view that
receives `certified_with_findings` and still styles, labels, groups or orders the `violated` row
as a failure must violate the amended requirement.** Task 3 Step 1 and Task 6 Step 1 are that
test, written twice — once on the badge that renders the status, once on the view that renders
the certificate.

**Word the extension so it does not narrow to convexity.** `violated` is convexity-only *by
implementation*, not by type: `CheckStatus` is a free enum on `CertificateCheck.status`, and
`CheckStatus.VIOLATED` is emitted at exactly one site
(`packages/pricing-core/src/pricing_core/modelling/objectives.py`:1007). `outcome_of` branches on
the status alone and has never asked which check carried it. A render rule written as "the
convexity check" would narrow silently the day a second check emits `violated`, so the amendment
is written on the status.

## Traps

1. **`OBJECTIVE_PAGE_CAP` is a capped sweep, and that is correct here — but `truncated` must
   reach the screen.** `listObjectives` pages to at most 5 × `PAGE_SIZE` (200) = 1000 artifacts
   and returns `truncated: true` when a cursor is still outstanding. The cap exists because
   `GET /custom-objectives` filters by `status` and `slug` only (OQ-605), so applicability
   filtering is client-side. A library view that dropped `truncated` on the floor would render a
   silently partial library — the exact defect the flag is in the return type to prevent.
   `ObjectivePicker.vue`:178 is the precedent for surfacing it.
2. **The five statuses are a set, not a ladder.** FR-163 writes the lifecycle as
   `draft → certified → review → approved → deprecated`, but the transition data carries two
   non-arrow edges: `objectives.py`:160-161 permits `review → {approved, certified}`. **Nothing
   in these views may present status as a sequence** — no progress bar, no step rail, no
   "next step" affordance. `objectives.ts`:31-34 already records this.
3. **`StatusBadge.vue` cannot be reused, deliberately.** It is hard-typed to `DatasetStatus` so
   the compiler enumerates its tone map; its own header records the bug that made that
   necessary. Widening it to a loose `string` would reintroduce that bug. Task 3 adds a sibling
   typed on the artifact statuses, keeping the exhaustive-`Record` property.
4. **Branch on the problem `code`, never on `status`.** `ProblemError` says so in its own
   docstring: several codes share a status. FR-166 specifies a 404 *"naming it"* when an
   objective has no certificate yet — a **normal** state for a `draft` objective, not an error
   screen.
5. **Nine checks, always.** FR-158 and `battery_is_exactly` mean a certificate carrying
   fewer is a failure of the run, not a smaller certificate. The view renders what the payload
   carries and must not silently render eight rows as if complete.

- [ ] **Step 3: Write the view**

```vue
<script setup lang="ts">
/**
 * `02` §5.3's Objective certificate, `/objectives/:id/certificate`.
 *
 * **FR-152, as amended 2026-08-25: a `violated` check is a finding, not a failure.** This
 * view is the one FR-24 named as carrying that obligation, and the amendment is what
 * discharged it. Concretely: `violated` is never styled, labelled, grouped or ordered as a
 * failure; the certificate reads as blocked only when `overall` is `failed`; and where a check
 * is `violated` the declared hessian clipping strategy is shown beside it, because the finding
 * without the strategy is the half an Approver cannot act on.
 *
 * **Nine checks, always** (FR-158). A payload carrying fewer is a failure of the run, not
 * a smaller certificate, so the count is stated rather than quietly rendered.
 *
 * **No convexity heatmap.** The §5.3 cell names one; `CertificateCheck` is name/status/detail
 * and `SamplingSpec` carries only grid parameters, so there are no per-point hessians to plot
 * at any depth. Under FR-24 that cell binds nothing beyond the presentation rule above, and
 * under OQ-587's floor rule a heatmap would be a new requirement plus a contract change.
 */
import { onMounted, ref } from "vue";
import { getObjective, getObjectiveCertificate, type CustomObjective, type ObjectiveCertificate } from "@/api/objectives";
import { ProblemError } from "@/api/problem";
import CheckStatusBadge from "@/components/CheckStatusBadge.vue";

const props = defineProps<{ id: string }>();

/** §4.7's battery size, held to by `battery_is_exactly` (FR-158). */
const EXPECTED_CHECKS = 9;

const objective = ref<CustomObjective | undefined>(undefined);
const certificate = ref<ObjectiveCertificate | undefined>(undefined);
const uncertified = ref(false);
const failure = ref<string | undefined>(undefined);

const OVERALL_LABEL = {
  certified: "Certified",
  certified_with_findings: "Certified with findings",
  failed: "Certification failed",
} as const;

onMounted(async () => {
  try {
    objective.value = await getObjective(props.id);
  } catch (error) {
    failure.value = error instanceof Error ? error.message : String(error);
    return;
  }
  try {
    certificate.value = await getObjectiveCertificate(props.id);
  } catch (error) {
    // FR-166 specifies a 404 naming it, and a `draft` objective legitimately has no
    // certificate. Branch on the code, never on the status — several codes share 404.
    if (error instanceof ProblemError) uncertified.value = true;
    else failure.value = error instanceof Error ? error.message : String(error);
  }
});
</script>

<template>
  <section class="p-6">
    <h1 class="mb-1 text-xl font-semibold">
      Objective certificate
      <span v-if="objective" class="font-normal text-slate-500">
        — {{ objective.slug }} v{{ objective.version }}
      </span>
    </h1>

    <p v-if="failure" class="text-sm text-rose-800">{{ failure }}</p>

    <p v-else-if="uncertified" class="text-sm text-slate-600">
      This objective has not been certified yet. Certification produces the evidence an Approver
      reads; until it runs there is no certificate to show.
    </p>

    <div v-else-if="certificate">
      <p class="mb-4 text-sm">
        <strong>{{ OVERALL_LABEL[certificate.result.overall] }}</strong>
        <span class="text-slate-500">
          — {{ certificate.result.checks.length }} of the {{ EXPECTED_CHECKS }} checks §4.7
          requires
        </span>
      </p>

      <table class="w-full text-sm">
        <thead>
          <tr class="text-left text-slate-500"><th class="py-1">Check</th><th>Result</th><th>Detail</th></tr>
        </thead>
        <tbody>
          <tr v-for="check in certificate.result.checks" :key="check.name" class="border-t border-slate-200 align-top">
            <td class="py-1">{{ check.name }}</td>
            <td><CheckStatusBadge :status="check.status" /></td>
            <td>{{ check.detail }}</td>
          </tr>
        </tbody>
      </table>

      <p class="mt-4 text-xs text-slate-500">
        Sampled over {{ certificate.result.sampling.n_points }} points, seed
        {{ certificate.result.sampling.seed }}. A convexity share is only meaningful alongside
        the grid it was measured on (§4.7).
      </p>
    </div>
  </section>
</template>
```

## Proposals for the roadmap's §14 question-4 block

Proposals, not changes (`CLAUDE.md` §14). Both are owned by the maintainer because both are
spec changes under §0's table and WK-664 closes without building either.

1. **`02` §5.3's Custom metric library cell promises a link to a view §5.3 never registers**,
   citing FR-162 — an API requirement whose predicate is *"create, read, certify, read the
   certificate, submit for approval, and list usage"* and which says nothing about a link. This
   is a third instance of the pattern FR-24 found twice among its seven carve-outs, and
   FR-24 already disposes of it: the cell is not a carve-out, so it binds nothing. Nothing
   is broken. What is worth deciding is whether `02` should register a metric-certificate view
   at all — `MetricCertificate` exists (FR-157, FR-162), `GET
   /custom-metrics/{id}/certificate` is built, and an approver of a metric is in the same
   position FR-166 was written to fix for objectives. **Owner: maintainer.**

2. **The SPA route `/metrics` and the Prometheus endpoint `/metrics` collide under same-origin
   serving**, which no current deployment uses. `backend/src/app/api/health.py`:137 serves the
   latter unauthenticated under FR-443. Neither is renamed by this slice: the collision is
   latent, and the scrape path is the one with an external consumer. The decision belongs to
   whoever specifies production serving — a path prefix for the SPA, a separate host, or a
   renamed view route. **Owner: maintainer.**

3. **Three §5.3 items are deferred with no slice able to own them**, because each needs a
   requirement or a contract field before any frontend work can start. They are listed here so
   the deferral outlives this plan, which `CLAUDE.md` §2 freezes at today's date.
   - *Loss-curve preview at chosen parameter values* (`02` §5.3:2592). No §5.1 route evaluates a
     loss over a parameter grid; the eight objective routes are create, list, detail, derive,
     certify, certificate, submit, usage. A new endpoint and a numbered requirement come first.
   - *A link to the metric certificate* (`02` §5.3:2594). Proposal 1 above is the same item seen
     from the other side: the link is un-buildable until §5.3 registers the view.
   - *Convexity heatmap over the sampled `(y, f)` domain* (`02` §5.3:2593). `CertificateCheck`
     is name/status/detail and `SamplingSpec` carries only grid parameters, so the per-point
     hessians a heatmap needs are absent from the contract at every depth. This is an ADR-704
     `model-schema` change before it is a chart, and it should be weighed against what the
     nine checks already tell an approver — `convexity`'s `detail` string carries the finding
     that the heatmap would illustrate.

   **Owner: maintainer** for all three. Each is a spec change under `CLAUDE.md` §0's table, and
   WK-664 closes without building any of them.

**Spec coverage.** Every requirement in the scope table maps to a task: FR-167 → Tasks
4-5; FR-166 → Tasks 2 and 6; FR-162 → Task 2 (and finding 4 for the half that is not
owed); FR-158 → Task 6 Step 1's third test; FR-152 → Tasks 1, 3 and 6; FR-153
and FR-164 → Task 4's row shape; FR-163 and FR-154 → Task 3's
`ArtifactStatusBadge` and trap 2; FR-150 → the editor's deferral; FR-148 → Task 6
Step 1's second test. The five §5.3 items with no task — editor, `/derive` display, loss-curve
preview, heatmap, metric-certificate link — each carry a §13 verdict and a named owner in the
item-by-item table, and the three the maintainer owns are repeated in the roadmap proposals so
they survive this plan being frozen. Nothing in the three cells is left silent, which is the
condition `CLAUDE.md` §13 imposes and the reason a "list only" scope was rejected.

**Placeholders.** Three literals are deliberately marked as unverified rather than left to look
settled: the `applicability` shape in Task 5 Step 1, the problem `code` in Task 6 Step 1, and
`hessian_strategy`'s generated field name in Task 6 Step 3. Each carries the command that
resolves it and the reason a guess is worse than a lookup. Nothing else is deferred.

**Type consistency.** `ArtifactRow` is defined once in Task 4 and imported by both views in
Task 5. `ArtifactStatus` (Task 3) is the union of `ObjectiveStatus` and `MetricStatus`, the same
union `ArtifactRow.status` uses. `CheckStatus` is read from the generated schema in Task 3 and
consumed only through `<CheckStatusBadge>`. `getObjective` / `getObjectiveCertificate` are named
identically in Tasks 2 and 6.

**One thing an executor should not silently fix.** If `pnpm --dir frontend generate:api` shows
`usage_count` absent from `CustomObjective` or `CustomMetric`, stop. That field is OQ-603's
decision and FR-167's obligation; its absence is a contract gap to raise, not a column to
drop from the table.
