# W6b-1a — Model detail, the non-GLM arms: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give `/models/:slug` a truthful rendering of a fitted GBM and a fitted EBM, of a
quantile bound's link to the model it bounds, and of the transparency artifact and surrogate
relationship that are a non-GLM model's answer to a relativity table.

**Architecture:** One narrowing seam in `frontend/src/api/models.ts` — arm types and
`model_type` narrowers taken from the generated schema — and four presentational components
the existing view dispatches to. The GLM arm is not touched except where the slice's own
subject reaches it (the surrogate notice, and the fitted-state check that today calls every
fitted non-GLM model unfitted). Nothing new is fetched except
`GET /models/{id}/transparency`, and that only for a non-GLM model.

**Tech Stack:** Vue 3 Composition API with `<script setup lang="ts">`, TypeScript, Tailwind,
Vitest + `@testing-library/vue`, types generated by `openapi-typescript` from
[`../contracts/openapi/generated.json`](../contracts/openapi/generated.json).

**Spec:** [`../specs/02-modelling.md`](../specs/02-modelling.md) — §4.4 (the `ModelSpec`
tagged union), §4.8 (`Model` and the three fit results), §4.9 (`TransparencyArtifact`),
§5.1 (the two reads this view makes), §5.3 (the Model detail row).

## Global Constraints

Copied from [`../../CLAUDE.md`](../../CLAUDE.md) §2–§3 and
[`../../.claude/skills/vue-frontend/SKILL.md`](../../.claude/skills/vue-frontend/SKILL.md).

  shared shape once and generates the frontend TypeScript from it. Types come from
  `@/api/generated/schema`, regenerated with `pnpm --dir frontend generate:api`; the directory
  is git-ignored and never committed.
- **Vue 3 Composition API with `<script setup lang="ts">` only.** No Options API, no JSX.
- **A JavaScript number is a float64.** A field whose contract declares it an exact decimal
  string stays a `string` on the way through — never `parseFloat` one (FR-OVR-7).
- **Every non-2xx is a `ProblemDetail`, and you branch on `code`, not `status`.**

## 2. Scope — what this slice deliberately does not build

Each exclusion is a boundary, and each says why rather than merely saying no. **None of them
is booked to another slice** (§0).

- **The diagnostics view, and every one of its charts.** `GET /models/{slug}/diagnostics` is
  not called by this plan and no diagnostics type is imported. This plan touches
  `ModelDetailView.vue` and adds four components beside it; no file under
  `frontend/src/views/` other than `ModelDetailView.vue` is created or modified.
- **Any chart at all.** NFR-OVR-10 attaches an accessible tabular equivalent to *each* chart,
  and the fallback is not built. A chart added here would enlarge the retrofit surface that a
  later fallback slice has to cover — the same argument the map makes for not doing the
  fallback first. Every quantity this slice renders is rendered as a table or a definition
  list, which needs no fallback because it *is* one. `vue-echarts` is not imported by any file
  this plan touches, and the check is mechanical (§5).
- **`POST /models/{id}/transparency`.** Building an artifact is a 202-plus-Job interaction —
  idempotency key, job polling, a status stream — and none of that is model *detail*. Where a
  non-GLM model has no artifact the view says so and names the endpoint in prose; it does not
  offer the button. Recorded in §6 as unowned.
- **The Contents-cell items the common arm still owes** — confidence-interval *bars* (the view
  renders intervals as numbers), the lineage strip, and `flags`. `02` §5.3's Model detail cell
  names all three and none is built. They belong to the arm this slice does not claim, and
  claiming them here is the widening this plan is written to avoid. Recorded in §6 as unowned.
- **Listing a central model's bounds on the central model's own page.** There is no read that
  answers it — see §6, E2.
- **Any change to `docs/specs/` other than the one Task 7 makes.** The draft excluded spec
  changes outright, on the ground that E3's spec-versus-code disagreement was unresolved. It
  is resolved at review — the specification is the wrong side — and
  [`../../CLAUDE.md`](../../CLAUDE.md) §0 requires that a disagreement be *resolved*, not
  carried. Task 7 corrects `02` §4.8's EBM example and nothing else in `docs/specs/`; no
  requirement row, no ID, no section number is touched.
- **Any change to `packages/model-schema`.** Every shape this slice needs already exists in
  the generated contract; the plan verified each one before assuming it.

would bury the slice's real diff inside a large move. The asymmetry is deliberate and
recorded rather than tidied.

Append to `frontend/src/api/models.ts`:

```ts
export type GlmSpec = components["schemas"]["GlmSpec"];
export type GbmSpec = components["schemas"]["GbmSpec"];
export type EbmSpec = components["schemas"]["EbmSpec"];
export type GbmFitResult = components["schemas"]["GbmFitResult"];
export type EbmFitResult = components["schemas"]["EbmFitResult"];
export type EbmTerm = components["schemas"]["EbmTerm"];
export type TransparencyArtifact = components["schemas"]["TransparencyArtifact"];

/**
 * The GBM arm is two `model_type` values, not one.
 *
 * `02` §4.4, amended 2026-08-17: `GbmSpec.backend` was removed because two fields held one
 * fact, and `model_type` — the discriminator the union already turns on — is what survived.
 * So xgboost and lightgbm are one arm with the backend written into the tag, and a narrower
 * that forgets the second renders an empty page for half the boosters this platform fits.
 */
export function gbmSpec(model: Model): GbmSpec | null {
  const spec = model.spec;
  return spec.model_type === "xgboost" || spec.model_type === "lightgbm" ? spec : null;
}

export function ebmSpec(model: Model): EbmSpec | null {
  const spec = model.spec;
  return spec.model_type === "ebm" ? spec : null;
}

export function gbmFit(model: Model): GbmFitResult | null {
  const fit = model.fit_result ?? null;
  return fit?.model_type === "xgboost" || fit?.model_type === "lightgbm" ? fit : null;
}

export function ebmFit(model: Model): EbmFitResult | null {
  const fit = model.fit_result ?? null;
  return fit?.model_type === "ebm" ? fit : null;
}

/**
 * Where the model a bound bounds lives, or `null` if this model is not a bound.
 *
 * FR-MODEL-78 requires a bound to share its central model's Model Family, and the platform
 * refuses a mismatch before a Job exists (`MODEL_INTERVAL_PAIR_INVALID`, compared on family
 * slug, dataset version, split ref and the factor set). The slug on this model is therefore
 * the central model's slug, and `interval_for.model_version` is its version — both read off
 * the contract. `interval_for.model_id` is a bare UUID and no read resolves one to a route,
 * which is why this returns the slug rather than it.
 */
export function boundCentral(
  model: Model,
): { slug: string; version: number; alpha: number } | null {
  const bound = gbmSpec(model)?.interval_for ?? null;
  if (bound === null) return null;
  return { slug: model.model_family_slug, version: bound.model_version, alpha: bound.alpha };
}

/**
 * The model's most recent transparency artifact (FR-MODEL-84).
 *
 * Addressed by **id**, not slug — `02` §5.1 declares `/models/{id}/transparency` — and it is
 * a 404 for a model that has never had one built. FR-MODEL-33 makes the artifact an
 * obligation for a non-GLM model only, so a GLM's 404 is not a state worth rendering and
 * this is not called for one.
 */
export function getTransparency(modelId: string): Promise<TransparencyArtifact> {
  return request<TransparencyArtifact>(`/models/${encodeURIComponent(modelId)}/transparency`);
}
```

**The slot layout is the whole difficulty, so it is written down rather than inferred.** The
built `EbmFitResult`, `EbmNumericBins` and `EbmCategoricalBins` agree on it:

- `bins` is a list, positional against `feature_order` — bin `i` belongs to feature `i`. It is
  not a map keyed by feature name.
- `term_features` holds **integer indices** into `feature_order`, not names.
- A numeric feature with `c` cuts gives its term `c + 3` slots: slot 0 unused, slots 1 through
  `c + 1` the populated bins, slot `c + 2` the trailing missing-value slot. Slot 1 is below
  `cuts[0]`; slot `j` for `2 <= j <= c` spans `cuts[j-2]` to `cuts[j-1]`; slot `c + 1` is at or
  above `cuts[c-1]`.
- A categorical feature with `L` levels gives `L + 2` slots: slot 0 unused, slot `i` is
  `levels[i-1]`, slot `L + 1` is missing.
- A `bin_weights` entry of zero marks the unused base slot, the missing slot, and any bin no
  row landed in.

```vue
<script setup lang="ts">
import { computed } from "vue";

import type { EbmFitResult, EbmSpec, EbmTerm } from "@/api/models";

const props = defineProps<{ spec: EbmSpec; fit: EbmFitResult }>();

/**
 * The bin labels of one univariate term, in slot order and without slot 0.
 *
 * With `c` cuts the term carries `c + 3` slots — the unused base slot, `c + 1` populated
 * bins, and a trailing missing-value slot. Slot 0 is never reached by a lookup, so rendering
 * it produces a bin with a 0.0 score that reads as a real level with no effect. An off-by-one
 * here does not fail loudly; it renders a shifted shape function that still looks like one.
 */
function labels(fit: EbmFitResult, term: EbmTerm): string[] {
  const bins = fit.bins[term.term_features[0]!];
  if (bins === undefined) return [];
  if (bins.kind === "categorical") return [...bins.levels, "missing"];
  const cuts = bins.cuts;
  const inner = cuts.slice(0, -1).map((low, i) => `${low} – ${cuts[i + 1]}`);
  return [`< ${cuts[0]}`, ...inner, `≥ ${cuts[cuts.length - 1]}`, "missing"];
}

const univariate = computed(() =>
  props.fit.terms
    .filter((term) => term.term_features.length === 1)
    .map((term) => ({
      name: term.term_name,
      rows: labels(props.fit, term).map((label, i) => ({
        label,
        // Display index `i` is slot `i + 1`: slot 0 is dropped, not rendered.
        score: (term.scores as number[])[i + 1] ?? 0,
        sd: (term.standard_deviations as number[])[i + 1] ?? 0,
        weight: (term.bin_weights as number[])[i + 1] ?? 0,
      })),
    })),
);

const interactions = computed(() =>
  props.fit.terms
    .filter((term) => term.term_features.length === 2)
    .map((term) => ({
      name: term.term_name,
      features: term.term_features.map((i) => props.fit.feature_order[i] ?? "?").join(" x "),
    })),
);
</script>
```

The template renders the intercept and the spec's max bins, max rounds and interaction budget
as a definition list; one table per univariate term, its `aria-label` being the term name
followed by "shape function", with the columns Bin, Score, Std dev and Weight; a row marked
"unpopulated" in words wherever the weight is zero; and, for each interaction, its name, its
two features, and the sentence that a two-dimensional surface is not tabulated here.

**Why an interaction term is named but not tabulated.** A pair term is a grid, and the only
honest tabular rendering of a grid is a matrix that is a heatmap in all but name. §2 excludes
charts, so the panel says the term exists, says what it is over, and says why its surface is
not shown — rather than silently dropping a term the fit actually contains.

## 6. Escalations — routed to the W6b work lead, decided by nobody here

[`../../CLAUDE.md`](../../CLAUDE.md) §10: a genuinely open design choice is never silently
picked. Each of these carries options and a recommendation, and **none is booked to another
slice** (§0).

**E1 — a model reference is a UUID, and no read resolves one to a route.**
`GlmSpec.approximates_model_id`, `glm_approximation.approximating_model_id`,
`interval_for.model_id` and `Model.parent_model_id` are all bare UUIDs. The only model read
addressed by identifier is the one on slug, so a UUID cannot become a link. Options: (a) render
the id as text, no navigation; (b) derive the surrogate's slug from the source model's — the
backend appends a fixed suffix when it builds one — and link to that; (c) add a by-id model
read, which is a spec change and so not a code slice's to make. **Recommendation: (a) now, and
(c) proposed.** (b) is refused on the standing rule: the suffix is a backend convention, and a
frontend that re-derives it is the second source of truth this repository refuses everywhere
else. The quantile bound is the one case that does link, and it links for a different reason —
FR-MODEL-78 makes the bound share its central model's family slug and the platform enforces it,
so the slug is read off the contract rather than derived from a name. **Unowned pending a
work-lead line.**

**E2 — a central model cannot list its bounds.** The relationship is stored on the bound
(`interval_for`), and the paired bounds are loaded only on the prediction path, where they
reach the client inside the uncertainty block of a prediction response. So this slice renders
the bound-to-central direction and not its reverse. Options: leave it one-directional and say
nothing on the central page, or specify a read that answers it. **Recommendation: leave it,
and record it.** Having the client list every model in the family and filter for bounds would
be a screen deriving a relationship the API declines to answer. **Unowned pending a work-lead
line.**

**E3 — spec and code disagree; the specification is the wrong side, and Task 7 fixes it**
