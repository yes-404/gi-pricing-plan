# ADR-0002 — model-schema is the single source of truth for shared shapes

- **Status:** accepted
- **Date:** 2026-08-14
- **Deciders:** maintainer
- **Related:** FR-OVR-6, FR-OVR-2, ADR-0003

## Context

The same shapes (a GLM specification, a rate table, a validation report) are needed by
`pricing-core`, the backend API, the frontend, the pipelines, and the on-disk artifact
format. Defining them independently in Pydantic, TypeScript, and a JSON Schema guarantees
drift, and drift in a pricing artifact is a mispricing incident, not a typing annoyance.

## Decision

`packages/model-schema` holds Pydantic v2 models for every shape crossing a module
boundary or persisted as an artifact. Everything else is generated from it:

| Target | Generated by | Committed to |
|---|---|---|
| JSON Schema (artifact validation, external consumers) | `model_schema.export:json_schema` | `docs/contracts/schemas/` |
| OpenAPI 3.1 | FastAPI from the same models | `docs/contracts/openapi/` |
| Frontend TypeScript types | `openapi-typescript` | `frontend/src/api/` (git-ignored, built) |

Rules:

- `model-schema` depends on Pydantic only. No SQLAlchemy, no FastAPI, no Polars.
- Persisted artifact models carry an explicit `schema_version` and a documented migration
  function; readers must accept every historical `schema_version`.
- CI regenerates all three targets and fails if the working tree differs from the
  committed output.
- A shape used in exactly one module and never persisted may stay local to that module —
  the rule is about *shared* and *persisted* shapes, not about all types.

## Consequences

**Positive** — one place to change a contract; the frontend cannot invent a field;
artifacts are externally validatable with plain JSON Schema tooling; API docs are always
current.

**Negative** — a contract change touches a generated-files diff in every PR; Pydantic
constructs that do not map cleanly to JSON Schema (complex discriminated unions,
arbitrary `Callable`) must be avoided or expressed as tagged unions.

**Neutral** — schema versioning and migration become an explicit, ongoing maintenance
task rather than an implicit one.
