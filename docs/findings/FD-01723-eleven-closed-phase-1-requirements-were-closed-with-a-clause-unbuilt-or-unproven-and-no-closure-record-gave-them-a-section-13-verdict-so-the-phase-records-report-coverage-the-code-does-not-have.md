## Finding

**Proposed severity for the class: HIGH, on two limbs (FR-100, FR-127's GLM limb); the others are MEDIUM or LOW.**

*(Ruled 2026-10-14: the maintainer (by delegation), "2026-10-14 11:28:56 BST" in `to-lead.md`, RULED the class HIGH, because the class takes its worst limb and the register sorts on it. The per-limb table below stays authoritative for scheduling. The proposal above is kept as written.)*
Reasoning is in the last section. The thesis: each of these eleven requirements was closed by a Work in
Phase 1a or 1b with a clause the code does not build, or builds and no test can fail, and **no
closure record gave that clause one of `CLAUDE.md` §13's four verdicts**. The phase records then count
the requirement as evidenced, because `scripts/scope-audit.py` counts a requirement evidenced when *any*
test carries its marker. `CR-754` says so itself: *"`scope-audit.py` counts a requirement as evidenced
when *any* test carries its marker, so "120 of 136" means **declared-or-refused**, not built."*
(`docs/closures/CR-754-…:111-112`.)

**The omission, measured.** The predicate, one command, at the tree above:
`git grep -nE "\b<id>\b" -- docs/closures` for each of the eleven ids. It returns **one hit for FR-6**
(`CR-819-…:128`, a different property, below), **three for NFR-467** (`CR-721-…:93,94,105`) and
**no hit for the other nine**. A closure record that lists "every unevidenced requirement with a
verdict" (`CR-721-…:111`) cannot list a requirement its own coverage count had already marked evidenced.
That is the mechanism, and it is the reason the gap survived two phase closes:
`CR-822-…:30` reports *"374 requirements in scope at the close audit, 276 evidenced, 98 unevidenced with a verdict each"*.
Evidenced meant a marker exists. It did not mean the requirement's text was read to its last clause.
