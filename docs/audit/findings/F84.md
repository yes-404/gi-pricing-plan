# F84 — 17 closure records have no discovery code and no guard: the migration cannot see them

**Raised** 2026-09-02 by the planner, while hunting a counterexample to the README `owner:` value;
**verified by the lead** at `ba31cd1`. Work item **W37-5c**, on the *blinds* limb. Phase 2.

## The population

**17 tracked files are closure records that the migration's discovery layer cannot see:**

- `docs/audit/work/*/README.md` — **16**
- `docs/audit/phases/1b/README.md` — **1**

**They are closure records, not indexes, and three independent sources say so:**

1. **§5.2** routes them to `closures/CR-0nnnn-*.md` with `kind: work` / `kind: phase`.
2. **§1.6's `CR` row** (`docs/notes/0019-one-id-per-document.md:152`) assigns that family to
   **`auditor` (`work`, `phase`)**; `lead` only for `review`.
3. **Their own first headings say it**: `# Work-item record — W11 (Scoring)`,
   `# Work-item record — W37-5b (the group-A preconditions slice)`, `# Phase record — 1b
   (Modelling Workbench)`.

**They are indexes of nothing.** The only property they share with the repository's other
`README.md` files is the filename.

## The gap, measured

- **`scripts/doc-id.py` contains no reference to `audit/work` or `audit/phases`** — grepped, zero
  hits. No discovery function reaches the path.
- **`_discover_closure_records` reads `docs/audit/closure-records.md` only** — its own docstring
  says so: *"one `###` heading per record."* The per-work READMEs are a different location it
  never visits.
- **No guard fires.** `audit-docs.py` knows the path for F-id citation checking, but that is a
  different check and not the migration's discovery. Nothing in `doc-id.py` censuses it.

## Why this is worse than F80, F81 and F82, despite looking smaller

**Those three abort.** Each is a guard correctly refusing to migrate a governed thing it has no
discovery code for, so a real `migrate()` run stops and says which. **This one is silent.** There
is no census over `docs/audit/work/`, so the 17 are not "discovered zero and flagged" — they are
**outside the question**. The run completes, reports success, and stamps them as whatever generic
rule reaches a `README.md`.

**A guard that aborts is a gap that announces itself. A population no census covers is a gap that
does not.** This is the same asymmetry `NT-0007` records for boundary metrics: absence of a
complaint is not evidence of coverage.

## What it costs today, concretely

Under the README row's second clause — *"every tracked `README.md` is in the family"* — these 17
take **`owner: lead`**, where §1.6's `CR` row assigns their true family to **`auditor`**. Nothing
downstream would catch it: **`lead` and `auditor` are both valid role stems**, so a check on the
value's *form* passes on the wrong value. That is the hole Ruling 88 named, in a new place.

**It is live rather than theoretical precisely because of this finding**: if something converted
them to `CR-` first, the README clause would never reach them. Nothing does.

## Falsifiable

Discharged when `migrate()` discovers all 17 as `CR-` drafts with `kind: work` / `kind: phase`,
**and** a census over that path names any file it cannot classify — proven on deliberately broken
input, per Ruling 83: the check must **name the unmatched unit**, never compare counts. Re-opened
if a later change moves closure records to a new location without extending the census, which is
the event that would recreate this silently.

**Not discharged by** the 17 merely being stamped with the right owner: the defect is that the
migration cannot see them, and a correct value reached by accident leaves the next corpus change
unprotected.
