# F71 — `python.yml` never triggered on `docs/**`, so a docs-only change could break any root test with CI green

Evidence essay for the register row self-named `(F71)` in `docs/audit/register.md`. The
finding: `.github/workflows/python.yml` — the only workflow that runs this repository's
root-level `tests/` suite — did not trigger on changes under `docs/**`, even though all
thirteen files in that suite read `docs/`. A docs-only PR could break any of them and CI
would report green. Filed and closed in the same motion: the gap is real, dated, and
already fixed.

## Provenance

Surfaced by the lead while investigating a separate matter (the mismatch that produced
F26's amendment, filed alongside this one) and fixed in the same PR that found it, #561.
Verified independently below against the merged tree, not taken from the PR body alone.

## The gap, verified directly

Before the fix (`origin/main` prior to `f2268916e5756eaf883ac6b18faf04c22d949ab6`),
`.github/workflows/python.yml`'s `paths:` filters (both `push` and `pull_request` blocks)
did not list `docs/**`. `.github/workflows/docs.yml` does watch `docs/**`, but it runs only
`scripts/audit-docs.py` — it does not run `pytest`. `python.yml` is the only workflow that
runs the repository's root `tests/` directory, and (verified by reading source, not
grepping paths, since `test_register_owed.py` builds its path with a `pathlib` join that a
substring search would miss) all thirteen files in that directory read something under
`docs/`. So a change touching only `docs/` — exactly the shape of filing a working note —
could not trigger `python.yml`, and any of those thirteen tests could break with nothing in
CI reporting it.

## The live instance — not hypothetical

Filing NT-0019 as `docs/notes/0019-...md` (the eighteenth-to-nineteenth note, PR #555,
2026-09-01) broke two of those thirteen tests on `main` for approximately a day, invisible
to CI the whole time because nothing triggered `python.yml` on that change:

- `test_audit_docs_notes_tombstone.py` asserted the literal string "18 working notes"; the
  corpus legitimately grew to 19 the moment NT-0019 landed.
- `test_notes_move_citations.py` forbids any living file citing the old `.claude/notes/`
  path; NT-0019 must name that path, since its own §4 step 4 specifies deleting those stubs
  as part of the migration it describes.

Both were real, reproducible failures against `main` — not a hypothetical mutation this
essay had to construct.

## The fix (PR #561, merged `f226891`, 2026-09-02T00:54:44Z)

Three changes landed together, deliberately, because a partial fix would have disarmed its
own detector:

1. `test_audit_docs_notes_tombstone.py` now cross-checks the script's own printed note count
   against an independent recount of the tree, rather than a frozen literal — it stops
   breaking every time a note is legitimately added.
2. `test_notes_move_citations.py`'s old-path exemption is narrowed to a documented, named
   two-member class (the note itself, and the auditor's own verification sweep that must
   quote the path to check it) rather than any structural rule that could self-widen.
3. **`docs/**` added to `python.yml`'s `paths:` filter, in both blocks** — the change this
   finding is actually about. Without it, fixing only the two tests would have left the next
   docs-only PR free to repeat exactly this failure, silently, again.

Verified in the merge commit rather than assumed: four broken-input proofs (inflating the
printed count reds fix 1; emptying the citation exemption reproduces the original PR #555
failure; removing only the newer exemption member reproduces a PR #560 failure while the
note stays correctly exempt, proving both members independently load-bearing; a genuine new
stray old-path citation is still caught), `pytest tests/` 122 passed, `audit-docs.py` all
checks passed, `ruff`/`mypy` clean, and the `python` workflow itself green on the merged
head.

## Why this is filed as its own finding, not folded into F26

The merge commit that fixed this gap describes it as "register finding F26's path-filter gap
with a live instance." **That attribution is wrong and is corrected in F26's own row**,
filed alongside this one: F26 is `.claude/roles/`+`.claude/skills/` having no CI trigger of
any kind (verified unchanged by this PR — `docs.yml`'s own filter still omits both paths).
This finding is a different workflow (`python.yml`, not `docs.yml`), a different symptom (a
covered checker's own trigger too narrow, not an uncovered directory), and a different fix
(a `paths:` addition to an already-triggering workflow, not adding a new directory to one).
The two are siblings in shape — both are a CI `paths:` filter missing something it should
watch — but siblinghood is not identity, and the register does not get a second copy of F26
by finding a second instance of the same *class* of mistake.

## Disposition

**Accept — the defect is fixed and verified, `f226891`; no owner is owed further work.**
Filed and closed in the same motion because, unlike F26 and F33, there is no residual gap
here to carry forward: the fix landed with its own broken-input proofs, in the same commit
that discovered it, for the reason stated in that commit ("a partial fix that disarms its
own detector is worse than either half alone"). The event that would reopen this row is a
regression in `python.yml`'s `paths:` filter dropping `docs/**` again, or a `docs/**` change
breaking a root test with CI still green.
