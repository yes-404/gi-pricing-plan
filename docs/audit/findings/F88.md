# F88 — discovery does not reach two populations §5.2 routes: one aborts every real run, one is silent

**Raised** 2026-09-02 by the W37-5c stamp-path executor, on the lead's instruction. Work item
**W37-6**, phase 2.

**Three limbs, one defect, and they are filed together deliberately.** Limbs 1 and 2 are
*"NT-0019 §5.2 says where this file goes, and no `_discover_*` function reaches it"*; limb 3
is the same shape one level up — a state the tooling can reach and cannot see — and it was
produced by this slice while filing these very findings. One finding for the shared
mechanism is worth more than three rows nobody connects. Limbs 1 and 2 differ only in whether
the migration **stops** or goes **blind** — the axis F80–F82 and F84 already sit on — and
limb 3 is blind in the same sense, about the register rather than about the migration.

## Limb 1 — `_discover_vendored_skill_manifests` aborts every real run, and would skip 25 if it did not

`scripts/doc-id.py`'s `_discover_vendored_skill_manifests` decides "already stamped" with
`if _docid.parse_header(skill_md) is not None: continue`. **That predicate is wrong for this
question**, and the two consequences are independent:

**It reads someone else's front matter as this migration's stamp.** `parse_header`'s own docstring
says so: *"A key outside the closed field set is not an error here — it lands in `.extra`
verbatim."* Every real `SKILL.md` opens with the harness's own block (`name:`, `description:`), so
`parse_header` returns a `Header` and the manifest is skipped as already-migrated. **Measured at
`359936b`, against the shipped symbols:**

| | |
|---|---|
| `.claude/skills/*/SKILL.md` | **46** |
| of those, `_is_vendored_skill_manifest` true | **28** |
| of the 28, `parse_header` returns a `Header` → skipped as "already stamped" | **25** |
| of the 28, `parse_header` raises `HeaderError` | **3** — `create-adaptable-composable`, `planning-with-files`, `vue-best-practices` |

**And it never gets that far.** The three that raise do so *inside the discovery function*, so
`_discover_vendored_skill_manifests(ROOT)` propagates `HeaderError` and a real `migrate()` run
aborts before the stamp loop is entered. Reproduced directly:

```
_discover_vendored_skill_manifests(ROOT) -> HeaderError:
  .claude/skills/create-adaptable-composable/SKILL.md:6: indented line — nested mappings
  are not in the closed field set (NT-0019 §1.5): '  author: github.com/vuejs-ai'
```

**This is F80/F81/F82 class and has had no id.** Those three are unconditional guards that refuse
to migrate a governed thing with no discovery code, and each was filed. This is a fourth stop with
the same effect on a run and none of the same visibility: it presents as a stack trace from a
YAML parser rather than as a guard naming what it cannot handle.

**It is distinct from F83, and the distinction matters.** F83's population is files that cannot
carry front matter **in any form** (59 `.json`, 1 `.yaml`, 2 more non-`.md` under `docs/`, plus
these 3 manifests) and its remedy is the exemption register now shipped in `audit-docs.py`'s
`UNSTAMPABLE_EXEMPTIONS`. **That register cannot discharge this limb**: it is read by check 35,
while the abort is a `parse_header` call inside `doc-id.py`'s discovery, which never consults it.
Two mechanisms on the same three files. Confirmed with the register's author.

## Limb 2 — `docs/audit/phases/1b/register.md` is discovered by nothing, silently

§5.2's row: *"`audit/register.md`, `audit/phases/1b/register.md` → one `findings/register.md`;
… the phase register's rows merge in with `phase: P1b` (NT-0003: no second copy)"*.

`_discover_register` reads `docs/audit/register.md` and nothing else — its own docstring says
*"Matched only at the legacy path"*. **Nothing reaches the phase register.** No guard fires, no
census covers it, and `migrate()` completes and reports success. That is F84's shape exactly, in a
population F84 does not range over, and it was found *by* F84's census: the file is a declared
exception there, carrying this reason, so that the gap is listed rather than folded into a `CR-`.

## Limb 3 — nothing stops two register rows claiming one finding id

**Added on the lead's instruction, after this slice produced the collision itself.** On
2026-09-02 two executors filed different findings as `F87` within an hour. Each had computed
the next free id from `main` correctly; neither could see the other's unmerged PR; there is
no allocator.

**The lead's account was that nothing would have caught it before the second merge
overwrote the first's file. Half of that is wrong, and the half that is wrong is the half
that would have been checked.** Measured with `git merge-tree` against the two real
commits:

```
added in both
  our    100644 4edba56... docs/audit/findings/F87.md
  their  100644 4278a53... docs/audit/findings/F87.md
```

**git reports the file collision as an add/add conflict and blocks the merge.** The essay
was never going to be silently overwritten. A check asserting "no two findings files share
an id" would therefore duplicate a guarantee git already gives, and would have been written
in the belief that it closed this gap.

**What has no guard is the register.** Two rows citing one id are inserted at different
offsets, merge cleanly, and `audit-docs.py`'s F-id citation check resolves the id to its one
file and passes — so the register can carry two rows for one finding and nothing says so.
That is the real hole, and it is one line of the same class as limbs 1 and 2: *a state the
tooling can reach and cannot see.*

**Discharged in this commit rather than carried**, because it is cheap and because leaving
it open would mean filing a finding about invisible states while leaving one open in the
document that reports them. `tests/test_findings_ids.py` asserts two invariants:

| | |
|---|---|
| every `docs/audit/findings/F<n>.md` heading names its own id | the mistake a renumber makes — this very finding was renumbered twice |
| no F-id is claimed by more than one register row's Finding-id cell | the state git permits and the audit passes |

Both are proven on deliberately broken input built in `tmp_path`, **never by mutating the
real tree** — which is limb 3 declining to commit the defect limb 1 of `F89` reports.
Measured at the filing tree: 76 register rows citing an id, 76 distinct; 25 findings files,
zero heading mismatches.

## Not proposed here

The disposition is the lead's. Naming the shapes without choosing: the "already stamped" test
could ask for **this migration's own marker** (`family:` present) rather than "front matter
parses", which is the positive-idempotency reading the rest of the module already uses; and the
three that raise need a disposition that is not `parse_header`'s to make — the exemption register
enumerates them by path if a fix wants a reconciled list rather than a second copy. Limb 2 needs
either a discovery function or a declared decision that the phase register is not migrated.

## Falsifiable

**Limb 1** is discharged when `_discover_vendored_skill_manifests(ROOT)` returns without raising
**and** returns the manifests that have not been stamped by *this* migration rather than the ones
whose front matter fails to parse — proven by a manifest carrying foreign front matter being
returned, not skipped. **Limb 2** is discharged when the phase register is claimed by a discovery
function or refused by a named decision, and its declared exception is removed in the same commit.
Re-opened if a later change adds a §5.2 route with no discovery behind it, which is the event that
recreates both.
