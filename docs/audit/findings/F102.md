# F102 — a document that is well-formed today and unclassifiable after the migration, with nothing before the migration able to say so

**Filed 2026-09-03 at `ac82256` by the lead, on the auditor's finding and its own recommendation.**
Work item **W37-6**, phase 2.

**Id allocation.** Swept across **every** ref — files and tokens — rather than `origin/main`,
per [`F99`](F99.md)'s constraint:

```
for r in $(git for-each-ref --format='%(refname)' refs/heads refs/remotes); do
  git ls-tree -r --name-only "$r" | grep -oE 'F[0-9]{1,3}\.md'
  git grep -hoE '\bF[0-9]{2,3}\b' "$r" -- docs/audit
done | grep -oE '[0-9]+' | sort -n -u | tail -1        → 101
```

Maximum is **101**; no `F102.md` exists on any ref. This record takes **F102**. `F98` remains
free and unallocated — its reclaim is the maintainer's under `CLAUDE.md` §5, per F99.

## The mechanism

**NT-0019's family classification is name-based, and it exists only on the far side of the
migration.** A file under `docs/` whose name matches no family rule classifies as `none`. §7(a)
requires **zero `none`**, so a single ordinarily-named new document fails that row.

**Before the migration runs, nothing reports this.** `audit-docs.py`, `register-lint.py` and the
full local gate all pass on such a file, because they check the properties a document has *today*
and the classification is a property it will only have *afterwards*. **The document is not
malformed. It is unclassifiable, and only on the other side of a transform that has not run.**

## The measured instance

The auditor added its second-measurement record as
`docs/audit/nt-0019-second-measurement-2026-09-03.md` — an ordinary, descriptive name in the
directory its siblings live in. Row (a) moved from `none=0` to `none=1`:

```
[FAIL] (a) every tracked file under docs/ parses to exactly one family, zero `none`
   denominator  473 file(s) under docs/ classified
   migrated     none=1
```

At both `0de529e` and `4b9117a` the same row is **PASS, `none=0`**. **Every local check on the
branch was green.** The only signal was `doc-id.py migrate --verify`, in CI, on a snapshot — and
it was nearly missed, because `--verify` is red by design on every PR under Ruling 102 §1, so a
reader checking the *job* rather than the *row* sees the expected red and stops. The auditor read
the row list inside the failing step and noticed it was not the one `main` produces.

**Resolved by precedent rather than by invention.** The migrated snapshot's own
`docs/REDIRECTS.csv` shows every sibling audit measurement record routing to `docs/research/`:

```
docs/audit/nt-0019-verification-and-impact-sweep.md  →  docs/research/RS-01000-…
docs/audit/file-census.md                            →  docs/research/RS-00998-…
docs/audit/ruling-acceptance-item-sweep.md           →  docs/research/RS-01001-…
```

The record moved to `docs/research/`; row (a) returned to **PASS, `none=0`**, research 18 → 19,
and the whole table returned to `main`'s baseline. **The destination was read out of the
migration's own output rather than chosen**, which is what makes it a precedent and not a guess.

## Why it is a finding and not a fix

**The class is "invalid only on the other side of a transform", and three variants of it landed in
a single day**, between two parties who were each actively watching for the others:

| variant | what was checked | what it was about |
|---|---|---|
| a count taken on the wrong side of the migration | the un-migrated source | the migrated population |
| a claim about a string checked against the wrong tree | the tree that was open | the tree the claim concerned |
| **this one** | the document as it is | the document as it will classify |

**The remedy for all three is the same and it is not care.** `--verify` is the only instrument
that sees any of them. That is Ruling 102 §1's argument — *the go-ahead becomes the script* —
arriving at a case its author did not have in mind, and arriving as an accident rather than as
reasoning.

**And the near-miss is part of the finding, stated as a property of the wiring rather than a
prediction about anyone's habits.** While §7 is red by design, **the `docs` job's pass/fail bit
carries no information about the change under review.** It was red before this regression and red
after it. A reader who consults the job status — which is what a status is for — learns nothing
either way, **and this holds for a reader who never skips anything.** The cost is not attention:
it is that **one of CI's three signals is switched off for the duration**, and the duration is
"until the migration lands".

**An earlier draft of this record said the by-design red "trains readers to skip the step".** That
is a claim about behaviour, the only data point is the auditor who found this, and **it did not
skip it** — so the sentence asserted as observed something nobody observed. Corrected on the
auditor's own objection to a finding written up from its work.

**Two checkable details make it structural rather than a matter of care.** The regression was
visible **only** in the row list inside the failing step — nothing in the job summary, the
conclusion or the step name differed. And it was caught only because that reader happened to hold
a baseline from having measured `0de529e` and `4b9117a` itself. **A reader without that baseline
could read the same log carefully and still see nothing wrong.**

**The row, not the job, is the unit of reading** — which is why the process obligation added for
this finding names row (a) specifically and says to compare it against `main`'s own output rather
than against zero.

## Falsifiable

Discharged when adding a file under `docs/` whose name matches no family rule **is reported to its
author before the PR is opened**, by one of:

- **The obligation as filed** — `docs/process/delivery-process.md` §11a: the author runs
  `doc-id.py migrate --verify <tmpdir> --ref HEAD` and reads row (a) against `main`'s own output.
  This is a procedure, so it is discharged only in the weak sense that it can be followed and
  skipped.
- **Or a check that does not depend on anyone remembering** — a pre-commit or gate step that
  classifies added `docs/` paths against the family rules without running the whole migration, and
  names the unclassifiable file.
- **Or, better and cheaper, the instrument distinguishing a new failure from the standing red.**
  `--verify` already knows its own verdict set, so recording the expected set and printing
  something of the form `18 FAIL (expected 17): (a) newly failing` — or exiting differently on a
  set change — **makes a new failure visible without any reader holding a baseline.** That is
  "the row, not the job, is the unit of reading" **mechanised**, which is strictly better than a
  process obligation asking people to read rows, and it would have caught this instance with no
  procedure at all. Proposed by the auditor; owner `executor-verify`; **not chosen here** — the
  process obligation above stands until something mechanical replaces it.

**Proven on deliberately broken input**, not only on a clean tree: a file added under `docs/` with
an ordinary descriptive name matching no family rule must be **named** by whatever mechanism is
adopted. The auditor's own record before it was moved is that input, preserved here by name:
`docs/audit/nt-0019-second-measurement-2026-09-03.md`, which every local check passed and row (a)
failed.

**Not discharged by** the second remedy merely existing. A classifier that has never printed the
name of an unclassifiable file has not been tested — `CLAUDE.md` §13, and the reason this
finding's own instance was found by an instrument rather than by a rule.
