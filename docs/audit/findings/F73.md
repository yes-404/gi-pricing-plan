# F73 — the lead-staleness nudge ladder cannot distinguish a legitimate long wait from a dead lead, because its own disambiguating signal was withdrawn for cause and never replaced

Evidence essay for the register row self-named `(F73)` in `docs/audit/register.md`. The
finding: `.claude/skills/reporter-cycle/scripts/nudge.py`'s three-signal liveness check
degrades into a periodic false alarm during any sufficiently long build, because all three
of its signals are legitimately stale in exactly that case, and the one signal that would
disambiguate — is real work actually in flight right now — was withdrawn under F31 and
nothing has replaced it since.

**Framing, stated up front because it is load-bearing.** This is not "the thresholds are
wrong" and not "reverse F31." F31's withdrawal was correct: `roster-state.md` was a heredoc
emitting a fixed string, lying more convincingly the longer it went unfixed. The finding is
narrower and different in kind — **F31's withdrawal had a downstream cost nobody costed at
the time**, and the nudge ladder has been running degraded ever since with nothing said
about it until now.

## Provenance

Raised by the reporter, relayed by the lead with one citation error the lead asked to have
corrected before filing (see "The citation, corrected" below). Verified independently
throughout, including against a live log file this review found on its own rather than
took on report.

## The mechanism, verified against the shipped script

`.claude/skills/reporter-cycle/scripts/nudge.py`'s own docstring states the design directly:

> "Multi-signal liveness (2026-09-01): a single-signal version of this check — the
> `.last_lead_status_ts` marker alone — fired a false positive while the lead was, in the
> same window, merging PRs, restarting executors and dispatching roles... This now checks
> THREE independent liveness signals and nudges only when every one of them is stale:
> 1. The marker file `.last_lead_status_ts`. 2. `eta.md`'s `**Updated:**` stamp. 3.
> `origin/main`'s newest local commit timestamp — the lead holds sole merge authority, so a
> recent merge is direct evidence of life."

`check_and_nudge`'s own docstring confirms the conjunction: *"nudge only if EVERY liveness
signal is stale."* This is a real, deliberate fix for the single-signal design's own
documented false positive, and it is not what this finding is about.

**The gap the AND-conjunction cannot close.** During an intentional long wait — a build,
a supervised migration run, anything the lead is correctly not interrupting — all three
signals go stale *together*, for the same reason, not independently: the lead is not
messaging the reporter (marker stales), not updating the ETA (eta.md stales), and nothing
is merging because nothing is ready to merge yet (`origin/main` stales). The three-signal
design defends against one lead being falsely flagged while genuinely busy elsewhere; it
does not defend against the lead legitimately doing nothing observable *by design*, which
a long build is.

`.claude/roles/reporter.md`'s own charter, read directly: *"Owns:... watch-the-watcher
(flags a stale `roster-state.md`...). Reads the watcher's published state; never polls
agents."* The fourth signal that would disambiguate — is any agent actually doing
anything right now — is architecturally exactly this: something the reporter would read
from the watcher's published state, never poll for directly. **`.claude/roles/
watcher.md:24`, read directly, forecloses using it**: *"...constant with a live
timestamp**, and the reporter must not treat `roster-state.md` as a [live source]."* F31
found `roster-state.md` to be a heredoc emitting a fixed string with only the timestamp
real; the charter has since been corrected to say so, in exactly these words. The
disambiguating signal exists in the architecture's shape and is disclaimed in its own
governing text.

## The live instance — not hypothetical, found in a log this review pulled itself

`~/gi-pricing-plan.local/handover/nudge.log` (local, not tracked, read directly):

```
2026-09-02T03:15:02Z - nudge sent - marker 218.7 min, eta 30.0 min, main 47.2 min (all >20.0 min threshold)
2026-09-02T03:45:01Z - nudge sent - marker 28.8 min, eta 30.0 min, main 77.2 min (all >20.0 min threshold)
```

Two nudges, thirty minutes apart. **`main`'s age grew from 47.2 to 77.2 minutes across
that gap — it did not reset — meaning no merge landed between them,** the direct, logged
signature of a build running rather than a fluke. `~/gi-pricing-plan.local/handover/
runtime-state.json`, read at filing time: `position.slice` is `W37-4`, `written_at`
`2026-09-02T02:02:13Z` — unmoved since (consistent with F72's own finding: `written_at`
only advances on a content change), meaning the slice had not progressed across this
entire window either. Three independent artifacts — the nudge log, the runtime state
file's own stale-by-design timestamp, and the arithmetic on `main`'s age — agree: W37-4
was mid-build, correctly, for over an hour, and the ladder fired twice on entirely correct
behaviour. An alarm that fires every thirty minutes on correct behaviour is one people
clear without reading, which this essay's own opening line calls worse than no alarm —
verified here as a real log, not asserted as a risk.

## The citation, corrected

The reporter's write-up, as relayed, cited the shared pattern as *"F69, F72 (bundled-data
invariant), and this detector."* **F72 is not the bundled-data invariant.** Verified
directly against the register: F72 is *"`written_at` records when a block's content last
changed, not when the writer last checked it"* — this session's own finding about
`write_runtime_state.py`, unrelated to bundled data. The bundled-data invariant is
`backend/tests/test_lineage.py::test_no_reference_rows_are_bundled_in_the_repository` —
confirmed to exist at that exact location — which is not a register finding at all; it is
a test, and it fired correctly on W37-4's own fixture tonight, catching what it was built
to catch. It does not belong in this trio and is not carried into it.

## The shared shape, verified against each member rather than asserted to match

**F69** (`write_runtime_state.py cycle` cannot clear a field): `position.slice` has no way
to express "no active slice" — omitting `--slice` silently preserves whatever was there
before, confirmed empirically when filed.

**F72** (`written_at` records change, not check): `written_at` has no way to express
"checked and confirmed live, nothing changed" as distinct from "not checked in a while" —
confirmed empirically, mtime included, when filed.

**F73** (this row): the runtime-state ecosystem has no way to express "work is actively in
flight" in the general sense the nudge ladder needs. `in_flight_expensive_verifications` —
the one field in artifact B that sounds like it should answer this — does not: its own
skill documentation scopes it narrowly to *"spec §8's 'announce an expensive verification,
check for one already in flight'"* protocol, a role explicitly announcing one specific
costly check, not a general "a slice is being worked" signal. `roster-state.md`, the
mechanism that once claimed to answer the general question, is discredited under F31 and
explicitly disclaimed in `watcher.md`'s own text.

**Three instances of one shape, in the same artifact family** — NT-0014's runtime-state
design (artifact B and its withdrawn sibling, roster state): *the state model is narrower
than what its own consumers need to ask of it.* Naming this as a shape rather than three
unrelated tickets is the point: patching the nudge ladder alone (a longer threshold, a
different weighting) would be the fourth consumer-side patch over the same underlying gap
F69 and F72 already showed is a modelling problem, not a per-consumer one.

## Amended 2026-09-02 — two more states the same shape produces, found the same night

Raised by the reporter against itself, relayed by the lead, verified independently rather
than taken from either — the same standard this row's original filing set. Both new states
are instances of the shape already named above (*the state model is narrower than what its
own consumers need to ask of it*); neither is discharged by the same remedy F73 already
proposes, which is why they are recorded as additions rather than folded silently into it.

### State — work complete, waiting on an external decision

The state this essay is itself being written in. Verified directly, not asserted: zero open
PRs (`gh pr list --state open`), `main` at `81e7c4e`, `eta.md`'s own headline reads "All work
merged... Team stood down... The only open maintainer decision is W37-6's go-ahead."
`nudge.log`'s own last entry, `2026-09-02T07:15:02Z`, reads `marker 209.0 min, eta 22.0 min,
main 21.9 min (all >20.0 min threshold)` — a live instance of exactly this state producing a
nudge. Distinct from the original finding's "long build" case in one load-bearing way: there
is no work in flight to detect. `origin/main` will not move because nothing is queued, not
because the lead is dead or the build is merely long; `eta.md` will not refresh because the
lead has nothing new to report, not because it cannot reach the file. **The "work in flight"
signal F73 already recommends would read `false` here too, correctly** — and a correctly
`false` signal cannot be what disambiguates "quiet because waiting on a human" from "quiet
because dead." This state needs a different signal than the one already proposed: something
closer to "is there a known, named, outstanding external dependency" (the `eta.md` headline
already carries this as prose — "the only open maintainer decision is X" — machine-readable,
it would be exactly the missing signal). Not sized here.

### State — a relaying agent's published field is checked; its internal narrative is not

**The sharper of the two, and the reporter's own report against itself.** Its cycle posts
`eta.md`'s headline verbatim by design (`report-spec.md` §1: *"Post the Headline line from
`eta.md` verbatim... Never extrapolate your own ETA"*), specifically so it cannot invent a
status — and, as far as this review can check, that published field was correct throughout
the window in question. Separately, in relaying two lead-staleness nudges — `nudge.log`
`2026-09-02T06:15:03Z` and `07:15:02Z` — the reporter is reported, by the lead, to have
included narrative beyond the bare signal ages `reporter.md`'s own Mechanism section actually
asks it to relay (step 4: *"Reporter reads the age from `<handover>/nudge.log`'s last line
and sends it to the lead via `SendMessage`"* — nothing about characterising build status),
stating that W37-4 was still building. **Independently verified: W37-4 (`#573`) merged at
`2026-09-02T04:06:14Z`** (`gh pr list --state merged`, cross-checked against `nudge.log`'s
timestamps) — **2h09m before the first relay and 3h09m before the second.** Between the
merge and the second relay, twelve further PRs merged (`#575`, `#576`, `#577`, `#578`,
`#579`, `#580` — six landed before the *first* relay alone — then `#581`, `#583`, `#584`,
`#585`, `#586`, `#587`), independently confirmed by timestamp against both relays.

**Sourcing, stated precisely rather than smoothed over.** The claim that these two specific
messages contained this specific narrative is the lead's own account, as the direct recipient
of them — not independently read by this review, which has no channel to another agent's
private message history. Asked the reporter directly, twice, for its own account or the exact
text; no answer had arrived by the time this row was pushed (noted, not filled in with an
invented corroboration). What *is* independently verified, without relying on the content of
either message: the merge timeline above (exact, from `gh`), that `nudge.log` fired at
exactly those two timestamps, and that `reporter.md`'s own stated procedure for a nudge relay
names only the age figure — narrative commentary on build status is not something the
charter asks for either way, which is a real gap regardless of whose account of the specific
wording is taken.

**One further layer, offered by the lead as a third instance rather than an excuse.** In
narrowing its own claim, the reporter is reported to have offered that its statements "may
have been accurate through 04:15" (`main` still at `0107d60`). Independently checked: false,
by nine minutes — `#573` merged at `04:06:14Z`, so `main` was already `39ee30c` by `04:15`.
If accurate as relayed, this is a sharper illustration than the original two: a hedge
produced while actively trying to be careful, still unverified against the one artifact
(`gh pr list` or `git log origin/main`) that would have caught it in seconds. Same
sourcing caveat as above — the exact wording is the lead's account, not independently read;
the nine-minute arithmetic is independently verified and does not depend on it.

**The mechanism, not just the instance.** Nothing in the reporter-cycle re-derives its
*narrative* the way it already, correctly, re-derives its structured facts —
`report-spec.md` §2 requires "Open PRs" and "Merged since your last post" to be derived each
cycle via `gh pr list` and `git ls-remote`/`git log`, never remembered, and the routine posts
this review read (`slack-reporter.log`, `02:30`-`04:15`) show that half working: the
`MERGED SINCE LAST POST` field tracked `main` accurately post by post. A free-text belief
about *why* nothing is moving is not covered by the same re-derivation discipline, and
nothing checks it the way `register-lint.py` checks a register row or `audit-docs.py` checks
a citation — the field that is checked (`eta.md`'s headline) is the one that stayed right;
the belief that was never checked is the one that was wrong, twice, over three hours. This is
the general form of both cases above and of F69/F72's own shape: a narrower model than its
consumers need, this time the consumer being the reporter's own narrative rather than a
downstream reader.

## Scope of this finding

- **Not fix-before-close.** The ladder is not wrong to alarm on three genuinely stale
  signals; it has no better information available, which is the finding.
- **Not a case for reversing F31.** Restated because it is the point most likely to be
  read past: `roster-state.md`'s withdrawal remains correct. A false signal removed and
  not replaced is still better than a false signal kept.
- **Proposed disposition** (a proposal; the verdict is the lead's): carry forward, unowned.
  Per the shared-shape framing, the recommendation is to extend artifact B's *model* with a
  general "work in flight" signal — re-derived each cycle the same way `position` and
  `in_flight_expensive_verifications` already are, Ruling-47(d)-compliant by the same
  construction — rather than add a fourth ad hoc signal to `nudge.py` alone or attempt to
  rehabilitate `roster-state.md`. That signal, once it exists, is what the reporter's
  charter already anticipates reading rather than polling for. Sizing, the exact shape of
  the new field, and ownership are not decided here — this row states the gap and the
  shared pattern, not the fix.
- **Falsifiable**: discharged by such a signal landing and the reporter's charter updated
  to read it, or by a corrected reading showing the existing artifacts already carry
  enough to disambiguate a long build from a dead lead.
- **Amendment 2026-09-02 — the two added states are not discharged by the same signal.**
  "Work in flight" reads correctly `false` in the "waiting on an external decision" state, so
  it cannot be what disambiguates that state from a dead lead; it needs a "known outstanding
  external dependency, named" signal instead, sketched but not sized above. The
  "published-checked, believed-unchecked" state is not a signal-design gap at all — it is
  that the reporter-cycle's free-text narrative is not re-derived the way its structured
  facts already are, which no artifact-B field fixes by existing. Recorded as two further
  gaps in the same family, each falsifiable on its own terms, not folded into the original
  disposition's single proposed fix.
