## Concerns — the defect and its reproduction

`scripts/audit-docs.py`'s check 1 (`main()`, the unlabelled first block) scans the raw text
of every `*.md` file under `docs/` for `re.finditer(r"\[[^\]]*\]\(([^)#\s]+)(#[^)]*)?\)", ...)`
and fails the gate if the captured target does not resolve to a real path (or an
`http(s)://`/`mailto:` URL). The scan runs against `f.read_text(...)` directly — it has no
concept of an inline backtick span or a fenced code block, so a doc that quotes a regex,
glob, or any other bracket-then-parenthesis construct verbatim is read exactly as if it were
a markdown link.

**Reproduced in one command**, against this tree, in a scratch file under `docs/` (removed
immediately after). The trigger substring is `get_eta`'s own time-of-day fragment — an
open square bracket, a space, a capital T, a close square bracket, then immediately an open
parenthesis, `\d{2}:\d{2}`, and a close parenthesis — written here with one deliberate extra
space before each opening parenthesis, and this paragraph's own description broken the same
way, **solely so this findings file does not retrip check 1 while describing the finding
that check 1 has no such awareness**; run without that inserted space, the identical
construction is what actually failed. Command executed: a scratch file was written with the
fragment once inside inline backticks and once inside a fenced block, then
`uv run python scripts/audit-docs.py` was run against the tree. Result: **two failures**,
one per occurrence, both reporting `broken link in _scratch-check1-repro.md`, each naming
the digit-and-colon portion of the fragment as an unresolvable target.

Both occurrences failed — **the inline-backtick one and the fenced one alike** — confirming
the defect is not limited to inline code; a fenced block gives no protection either. This is
the live incident that motivated filing: an early draft of `docs/audit/findings/F65.md`
quoted `get_eta`'s own regex verbatim, including that same fragment, and check 1 read it as
a link to a nonexistent path and failed the gate. It was worked around by rewording to
prose rather than fixed.

## Scope — class and population, measured

**Class:** any text matching `\[[^\]]*\]\([^)#\s]+\)` anywhere in a tracked `.md` file under
`docs/` is read as a link, regardless of code-span context — a syntactic pattern used as a
proxy for "this is a markdown link," with no exclusion for the one context (quoted code)
where the same syntax is common and never means that. `[^\]]` also matches newlines, so the
bracket half of the pattern can span line breaks; this did not produce any false positive in
the corpus below, but it means the proxy is looser than "one line" in the direction that
makes the class larger, not smaller.

**Current population — measured, not estimated.** Wrote a script (not shipped, run
ad hoc) that re-applies check 1's own regex to every file `docs/**/*.md` (930 matches
today), and for each match determines whether it sits inside a fenced code block or an
odd-parity inline-backtick span on its line, and whether its target currently resolves.
Result: **all 930 matches currently resolve** (0 real failures today, consistent with
`audit-docs.py` currently printing no check-1 failures), and **0 of the 930 sit inside a
fenced code block or an inline-backtick span** — the one candidate the script flagged
(`docs/specs/00-overview.md:218`) is not a genuine code-span hit; it is a cross-line
artifact of the bracket half matching across a newline into the following table row, not a
backtick-quoted construct, and its target is a real link (`../adr/0006-...`) that resolves.

**So the honest scope claim is: the population of currently-tracked docs that trip this
today is zero.** The defect is latent rather than live in the current corpus — every
existing bracket-label-then-parenthesised-target substring in `docs/` happens to be a
genuine link. It is a
forward-looking risk realised exactly once so far (the F65 draft, worked around before
merge), not a standing failure sitting in `main` today. A reader should not infer from this
row that any currently-committed doc is broken; none is.

## Is this the same shape as `a3b9c9e`'s pipe-count bound? Checked, not assumed

`a3b9c9e` (`fix(audit): the register table renders as three fragments after F52`, #529)
corrected `register-lint.py`'s table-end detection: bounding the table's end by "the last
row-shaped (pipe-heavy) line anywhere in the file" reached past the real table into a
fenced example table and prose containing pipes, and flagged ordinary lines that were never
part of any table. The commit's own framing: a boundary was drawn on a syntactic proxy — "is
this line pipe-heavy" — standing in for a semantic question — "is this line part of the
table" — and the proxy caught content the semantic question was never about.

Check 1 is the same shape: **"does this text match a bracket-label immediately followed by
a parenthesised target"** stands in for **"is this a markdown link"**, and the proxy fires
on quoted code that matches the syntax without meaning a link. The mechanism differs (a
regex with no code-span exclusion, vs. a line-shape bound with no table-boundary awareness)
but the class is the same: a syntactic proxy used where a semantic distinction (code span vs.
prose; inside this table vs. outside it) was needed, and the proxy was never scoped to make
that distinction. Read as a fair analogy, not a stretch — both are "the check cannot tell why
the text has this shape, only that it does."

## Filing this finding tripped it once more

**This finding's own first draft failed the gate on this same defect while being filed —
direct evidence the class is not narrow.** An earlier revision of this file quoted the
check's regex pattern and an illustrative bracket-then-parenthesis example directly in prose,
and running `python3 scripts/audit-docs.py` against it reported six failures, three from the
reproduction command's trigger fragment (once inline, once fenced, once in the shown FAILED
output) and three from the illustrative shorthand used three times in the analysis above.
The wording in this filed revision avoids unresolvable bracket-paren sequences in prose: the
reproduction paragraph above states the trigger construction in words, with a deliberately
inserted space breaking the bracket-then-parenthesis adjacency check 1's pattern requires, so
this file's own text does not match the pattern by construction, not by coincidence. Verified
by re-running `python3 scripts/audit-docs.py` against this filed revision: 0 check-1 failures
for this file (see the commit this file lands in for the full run).

## Decision — reasoning

**Carry forward, unowned.** The fix — skip matches whose position falls inside a fenced
code block or an odd-parity inline-backtick span before evaluating them as links — is a
small, scoped change to check 1 alone, but it is not made here: filing a finding and fixing
the defect it describes are different acts, and the fix is not scoped to this filing task.
Not filed as **fix before close**, because nothing in the current corpus is failing — there
is no close this blocks and no live breakage to fix before one. Recorded unowned rather than
guessed at a workstream; the natural next owner is whoever next touches `audit-docs.py`
check 1, or a dedicated small PR.

**Falsifiable, not permanent**: discharged by a fix to check 1 (adding code-span awareness,
regression-tested on a constructed input the way `a3b9c9e` tested its own bound) and
verified against a re-run of this row's own reproduction; or superseded if the maintainer
decides the current behaviour is acceptable and authors are expected to avoid the pattern in
prose instead.
