# F76 — an uncaught `HeaderError` in check 39 silently drops six later `audit-docs.py` checks (and every note from the ~30 that ran before it); the fix is already ruled and owned, this row is what tracks it

Evidence essay for the register row self-named `(F76)` in `docs/audit/register.md`. The
finding itself — `_ROW_FIELDS` rejects fields the `WK-`/`SL-` templates declare, and
`check_index_stable` calls the parser that enforces this with no exception handling — is
**not new**: `docs/plans/2026-09-02-w37-template-parser-conflicts-rulings.md`'s **Ruling
79**, merged in PR #581 (`b6a6f31`), already verifies it, rules the fix, and names the
owner. What is missing, and what this row supplies, is the register-side tracking that
PR #581's own squash-merge commit message claimed already existed: *"LARGER THAN REPORTED,
AND FILED SEPARATELY."* `grep -c "build_corpus\|skips six" docs/audit/register.md` returns
`0` at every tree checked in this essay. This row makes that claim true.

## Provenance

Dispatched by the lead as urgent, for exactly the reason above: a merged, durable commit

## The defect, verified directly against the shipped code, at `main` = `22adfe9`

`scripts/doc-index.py:268-270`:

```python
_ROW_FIELDS = frozenset(
    {"id", "family", "kind", "title", "status", "created", "owner", "phase", "work", "slice"}

```

`tree`, `corrected_by` and `relates` are not in this set. `docs/_templates/WK.md:26,28,29`
and `SL.md:27,30,31` (read directly) both declare all three inside the fenced block the
template's own comment instructs an author to copy verbatim. `_parse_row_block`
(`doc-index.py:289`) raises `HeaderError` on the first field it does not recognise —
`tree`, alphabetically and positionally first in the template.

`scripts/audit-docs.py:2207`, inside `check_index_stable` (check 39):

```python
corpus = _doc_index.build_corpus(ROOT)
```

No `try`. `check_index_stable` is the last of ten checks `check_ids_30_39()` calls
(`audit-docs.py:2239-2248`); `check_ids_30_39()` itself runs at `audit-docs.py:2686`,
immediately before six more checks with no exception boundary between any of them:
`check_open_question_mirror_status` (2689, check 23), `check_finding_citations` (2693,
check 25), `check_process_core_drift` (2696, check 26), `check_process_core_digest` (2699,
check 27), `check_plan_acceptance_standard` (2702, check 28), `check_register_grammar`
(2705, check 29). `main()` itself is called as `sys.exit(main())` (`:2720`) with no
enclosing `try` either.

**Line numbers are cited as of this tree and are not stable** — the lead's dispatch cited
`:436-455` for the same call sites, and Ruling 79 itself cited `:2183`/`:2662`/`:2665-2681`,
verified at an earlier commit (`9367eac`); neither matches this essay's `:2686-2705`/`:2207`,
and none of the three citations is wrong for the tree it was taken at. The file has grown
between each reading. Relative call order, not absolute line numbers, is the load-bearing
fact, and it reproduces identically across all three readings.

## The question the dispatch asked directly: silent, or a traceback?

**A traceback, not silence — confirmed by the captured run above, not asserted.** Exit code
`1`. A full Python stack trace to stderr naming the exact file, line and field
(`docs/roadmap.md:785: unknown row field 'tree'`) — in fact more specific about the root
cause than the audit's own structured failure messages usually are. This is **materially
different from, and less severe than**, the scan-roots precedent
(`tests/test_audit_docs_scan_roots.py`'s own stated reason for existing) that Ruling 79
analogises to: that defect was a vanished root causing five checks to silently *skip* while
the script still printed `All checks passed` and exited `0` — a false green. This defect
exits `1` and prints a traceback naming the exact defect; a CI reader sees a red job and,
reading the traceback, the precise cause. What is lost is not a signal that something is
wrong, but the audit's own structured report — no note from any of the ~30 checks that ran
before the crash, and no verdict from the six that never got the chance to run. **Ruling 79
itself says "a red gate that prints nothing"** — accurate for the audit's own report (true,
verified above: zero of `main()`'s own notes print), imprecise if read as "silent" in the
scan-roots sense (false: the process is loud, just not in the audit's own vocabulary). Worth
stating precisely because the dispatch asked which one holds, and because conflating this
with the scan-roots case overstates severity in one direction while understating scope in
another — see next.

## Broader than "six checks skip" — every earlier check's output is lost too

`audit-docs.py`'s `notes` and `failures` (`:131-132`) are module-level lists; every check
appends to them as it runs, and printing happens exactly once, at the very end of `main()`
(`:2707-2716`), after every check including `check_register_grammar`. An uncaught exception
anywhere before that point discards everything accumulated so far, not only what comes
after. Concretely, for this defect: checks 30-38 (the nine other NT-0019 id-standard checks,
which run and succeed *before* check 39 inside the same `check_ids_30_39()` call) have their
notes computed and silently dropped too, alongside checks 23, 25, 26, 27, 28 and 29, which
never run at all, and every check before line 2686 (broken links, requirement ids, open
questions, ADRs, spec sections, JSON schemas, and more) — all of it, dropped. The
captured traceback above shows this directly: zero lines of audit output precede it. Ruling
79's own count ("skips six unrelated checks") is correct for what never *runs*; it does not
separately name what already ran and still never gets *reported*, which is the entire rest
of the script.

## This is not a new decision — Ruling 79 already made it, and this row tracks it

`docs/plans/2026-09-02-w37-template-parser-conflicts-rulings.md`, **Ruling 79** (§§1-4,
read in full): verifies this exact defect (its own "PROBE 1", matching both reproductions
above independently), rules **"the templates are correct; `_ROW_FIELDS` is the defect...
the remedy is to *derive* the row field set from the family's template, never to widen a
transcription"** (§2), states four concrete obligations (§3) — delete `_ROW_FIELDS` as a
hand-written constant, derive it per-family from the templates via `_docid.py`, wire the
three previously-hardcoded fields (`tree`, `corrected_by`, `relates`) into
`_row_header_from_raw`, and make `doc-id.py migrate`'s row emission derived from the same
template — and names **"5. Owner: W37-6"** (§3), with acceptance criteria in §4: a
broken-input proof (a template's fenced block, copied into a fixture and parsed, must fail
today and pass after the fix), Ruling 70's mutation test applied to `doc-index.py`, and a
check that `kind:` is rejected on a `WK-` row (the "too permissive" half of the same defect).

**This is "the sibling item" the dispatch asked to be noted alongside this row**: Ruling
79 §4's first acceptance bullet — *"a check that copies each row template's fenced block
into a roadmap fixture and parses it... extend `tests/test_template_headers.py`, which
already reads these templates for the other parser"* — is not a second, separate defect. It
is the same ruling's own diagnosis of *why nothing caught this*: `test_template_headers.py`
feeds the templates to `_docid.parse_header` (a different, more permissive grammar) and
passes; nothing feeds them to the row parser that actually consumes a roadmap row. One
ruling, one owner, two acceptance items; this row cites both under the one owner rather than
splitting them.

## Scope of this finding

- **Not fix-before-close for this row.** The fix is `_ROW_FIELDS`, the templates, and
  `main()`'s exception boundaries — all inside `scripts/`, all Ruling 79's and W37-6's
  scope, per the dispatch's explicit instruction not to touch them here.
- **Filed, not re-decided.** Ruling 79 already made every decision this defect needs;
  this row's job is to make it a tracked, owed item (`register-owed.py`), which a
  plan-embedded ruling alone does not automatically become pre-migration.
- **One structural observation, not filed as a separate item**: Ruling 79's four
  obligations fix *this* trigger (the three specific fields). They do not add exception
  isolation to `main()` itself — the next uncaught exception anywhere in checks 1-39, for
  any other reason, would reproduce the same blast radius. Worth the lead's or W37-6's
  awareness; not sized or ruled here, and not this row's to decide.
- **Proposed disposition** (a proposal; the verdict is the lead's): carry forward with an
  owner — **W37-6**, per Ruling 79 §3 point 5, which is open and active.
- **Falsifiable**: discharged when Ruling 79's §4 acceptance items land (a broken-input
  proof that fails today and passes after the fix, Ruling 70's mutation test applied to
  `doc-index.py`, and the `kind:`-on-`WK-` rejection test), or by a corrected reading
  showing the defect does not reach real content the way this essay demonstrates it does.
