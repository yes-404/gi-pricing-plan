# F72 — `written_at` records when a block's content last changed, not when the writer last checked it

Evidence essay for the register row self-named `(F72)` in `docs/audit/register.md`. The
finding: `runtime-state.json`'s `written_at` field cannot answer the question a reader
actually asks of it. This is filed as an **expressiveness gap**, not a defect — the writer
behaves exactly as designed and exactly as a prior ruling requires; the artifact simply has
no field for the question a reader needs answered.

## Provenance

From the watcher, verified independently below rather than taken on report. The watcher's
own first draft called this a tool defect; that framing is corrected in its own section,
because filing it that way would collide with an existing, binding acceptance test.

## The live instance, read directly

`~/gi-pricing-plan.local/handover/runtime-state.json`, read at filing time:

```json
"position": {
  "written_by": "watcher",
  "written_at": "2026-09-02T02:02:13Z",
  ...
},
"in_flight_expensive_verifications": {
  "written_by": "watcher",
  "written_at": "2026-09-01T20:06:20Z",
  "entries": []
}
```

`position` is current to the minute. `in_flight_expensive_verifications` carries a
six-hour-old stamp against an empty list. **The stamp is truthful**: nothing has changed
in that block since 20:06:20Z. **The stamp is also useless for the question a reader
actually asks**, which is not "when did this last change" but "is this being maintained at
all right now, or is it the residue of a writer that stopped." Six hours of an empty list
is exactly what a healthy, idle system produces, and exactly what a dead writer's last
gasp looks like. `written_at` cannot tell the two apart.

## Why this is a gap, not a defect — verified against the mechanism and the ruling

`write_runtime_state.py cycle` (`.claude/skills/watcher-runtime-state/scripts/
write_runtime_state.py`) computes each block's new content from the current inputs, then:

```python
if "position" in existing and new_position_content == _block_content(old_position_block):
    new_position_block = old_position_block   # stamps and all, unchanged
else:
    new_position_block = {
        "written_by": "watcher",
        "written_at": now_iso,
        **new_position_content,
    }
```

Identical logic covers `in_flight_expensive_verifications`. When the freshly re-derived
content matches what was already on disk, the **entire old block — stamps included — is
carried forward untouched**; a new block, and a new `written_at`, is only constructed on an
actual content change. This was independently re-proven for this filing exactly as it was
for F69: two `cycle` calls with identical inputs, seconds apart, against the same seeded
file, leave `written_at` unmoved on both blocks (`git show` of the current script;
empirically re-run, not only re-read).

**This is not incidental — it is `docs/plans/2026-08-30-nt-0014-q1-q3-q4-rulings.md`
Ruling 47(d)'s own acceptance test, byte for byte.** Verified at its cited location,
`docs/audit/work/nt-0012-0013-0014-adoption/README.md:114`: *"Ruling 47(d)'s acceptance
test (a no-op cycle produces a byte-identical file, verified failing by hand against a
scratch mutation before confirming it passes against the real implementation — PR #506's
own test plan)."* Read verbatim, exactly as cited — no mis-citation found, though one was
looked for rather than assumed absent. A no-op cycle producing a byte-identical file is
only possible if `written_at` does **not** move when content does not change; the behaviour
this essay measures is the behaviour Ruling 47(d) requires, not a bug that violates it.

**The corrected framing, stated plainly.** The watcher's first draft read `.claude/roles/
watcher.md`'s "writes `position` and `in_flight_expensive_verifications`... each cycle" as
a claim that `written_at` should move every cycle, and filed the gap between that claim and
the tool's actual behaviour as a tool defect. Filed that way, this essay would have had to
either reject the finding or reopen Ruling 47(d) — a false choice, because the premise is
wrong: `watcher.md`'s "each cycle" describes the watcher's own decision to *re-derive its
inputs* and call `cycle` unconditionally (never skipping the call itself, never
comparing-and-deciding-not-to-invoke) — a claim about invocation, not about the timestamp
`cycle` then writes. **Behaviour satisfies the skill and the ruling; the artifact simply
lacks a field for what the watcher's first framing actually wanted to ask.** No field in
the current schema — checked directly, `written_by`/`written_at` are the only two
per-block metadata keys `write_runtime_state.py` or `.claude/skills/watcher-runtime-state/
SKILL.md` name anywhere — records "the writer looked at this and confirmed it live" as
distinct from "the content last changed at this time."

## Shared shape with F69

F69 (`write_runtime_state.py cycle` cannot clear a field — "no active slice" is
inexpressible): the position block's schema has no way to express "no active slice,"
because `_position_block_content` only overwrites a field when a value is supplied. F72
(this row): the schema has no way to express "checked and unchanged" separately from "not
checked recently," because `written_at` is the only per-block timestamp and it moves on
content change alone. Different fields, same mechanism-level shape — **the state model is
narrower than what its own consumers (a person reading the file, or a future automated
staleness check) need to ask of it.** One instance is an anecdote; two are a shape worth
naming together, per the watcher's and lead's own framing, verified against F69's actual
filed text rather than assumed to match.

## Mutation that must become detectable

Stop the writer process entirely. The artifact left behind is **byte-identical** to a
healthy writer's output from a cycle that re-derived its inputs and found nothing changed —
there is no reachable state today that distinguishes "the watcher is dead" from "the
watcher is alive and idle," using this file alone. `written_at` answers "when did content
last change," never "was this process alive as of now."

## Scope of this finding

- **Not a defect in `write_runtime_state.py`, `cycle`, or `watcher.md`.** All three are
  internally consistent with each other and with Ruling 47(d); nothing here asks for any of
  them to change their current behaviour.
- **Not fix-before-close.** F58 already carries the "no live process invokes the script on
  a schedule" gap as its own open row; this finding is about what the artifact could not
  tell a reader even if a live process were invoked reliably every cycle.
- **Proposed disposition** (a proposal; the verdict is the lead's): carry forward, unowned.
  The natural fix is an additional per-block field — a `checked_at` (or `derived_at`)
  timestamp, bumped unconditionally on every `cycle` invocation regardless of whether
  content changed, alongside the existing `written_at` which keeps its current,
  Ruling-47(d)-compliant, content-change-only semantics. That is a schema addition, not a
  behaviour change, and does not reopen Ruling 47(d) — the no-op-byte-identical test would
  need updating to exempt the new field specifically, which is a smaller, scoped change to
  make explicitly rather than a reason to leave the gap unaddressed. Sizing and ownership
  are not decided here.
