# F72 — `written_at` records when a block's content last changed, not when the writer last checked it

Evidence essay for the register row self-named `(F72)` in `docs/audit/register.md`. The
finding: `runtime-state.json`'s `written_at` field cannot answer the question a reader
actually asks of it. This is filed as an **expressiveness gap**, not a defect — the writer
behaves exactly as designed and exactly as a prior ruling requires; the artifact simply has
no field for the question a reader needs answered.

## Provenance

From the watcher, verified independently below rather than taken on report. The watcher's
own first draft called this a tool defect; that framing is corrected in its own section,
because filing it that way would collide with an existing, binding acceptance test.

## The live instance, read directly

`~/gi-pricing-plan.local/handover/runtime-state.json`, read at filing time:

```json
"position": {
  "written_by": "watcher",
  "written_at": "2026-09-02T02:02:13Z",
  ...
},
"in_flight_expensive_verifications": {
  "written_by": "watcher",
  "written_at": "2026-09-01T20:06:20Z",
  "entries": []
}
```

`position` is current to the minute. `in_flight_expensive_verifications` carries a
six-hour-old stamp against an empty list. **The stamp is truthful**: nothing has changed
in that block since 20:06:20Z. **The stamp is also useless for the question a reader
actually asks**, which is not "when did this last change" but "is this being maintained at
all right now, or is it the residue of a writer that stopped." Six hours of an empty list
is exactly what a healthy, idle system produces, and exactly what a dead writer's last
gasp looks like. `written_at` cannot tell the two apart.

## Why this is a gap, not a defect — verified against the mechanism and the ruling

`write_runtime_state.py cycle` (`.claude/skills/watcher-runtime-state/scripts/
write_runtime_state.py`) computes each block's new content from the current inputs, then:

```python
if "position" in existing and new_position_content == _block_content(old_position_block):
    new_position_block = old_position_block   # stamps and all, unchanged
else:
    new_position_block = {
        "written_by": "watcher",
        "written_at": now_iso,
        **new_position_content,
    }
```

Identical logic covers `in_flight_expensive_verifications`. When the freshly re-derived
content matches what was already on disk, the **entire old block — stamps included — is
carried forward untouched**; a new block, and a new `written_at`, is only constructed on an
actual content change. This was independently re-proven for this filing exactly as it was
for F69: two `cycle` calls with identical inputs, seconds apart, against the same seeded
file, leave `written_at` unmoved on both blocks (`git show` of the current script;
empirically re-run, not only re-read).

**This is not incidental — it is `docs/plans/2026-08-30-nt-0014-q1-q3-q4-rulings.md`
Ruling 47(d)'s own acceptance test, byte for byte.** Verified at its cited location,
`docs/audit/work/nt-0012-0013-0014-adoption/README.md:114`: *"Ruling 47(d)'s acceptance
test (a no-op cycle produces a byte-identical file, verified failing by hand against a
scratch mutation before confirming it passes against the real implementation — PR #506's
own test plan)."* Read verbatim, exactly as cited — no mis-citation found, though one was
looked for rather than assumed absent. A no-op cycle producing a byte-identical file is
only possible if `written_at` does **not** move when content does not change; the behaviour
this essay measures is the behaviour Ruling 47(d) requires, not a bug that violates it.

**The corrected framing, stated plainly.** The watcher's first draft read `.claude/roles/
watcher.md`'s "writes `position` and `in_flight_expensive_verifications`... each cycle" as
a claim that `written_at` should move every cycle, and filed the gap between that claim and
the tool's actual behaviour as a tool defect. Filed that way, this essay would have had to
either reject the finding or reopen Ruling 47(d) — a false choice, because the premise is
wrong: `watcher.md`'s "each cycle" describes the watcher's own decision to *re-derive its
inputs* and call `cycle` unconditionally (never skipping the call itself, never
comparing-and-deciding-not-to-invoke) — a claim about invocation, not about the timestamp
`cycle` then writes. **Behaviour satisfies the skill and the ruling; the artifact simply
lacks a field for what the watcher's first framing actually wanted to ask.** No field in
the current schema — checked directly, `written_by`/`written_at` are the only two
per-block metadata keys `write_runtime_state.py` or `.claude/skills/watcher-runtime-state/
SKILL.md` name anywhere — records "the writer looked at this and confirmed it live" as
distinct from "the content last changed at this time."

## Amended 2026-09-02 — mtime is unchanged too: nothing records liveness, not the JSON alone

The lead tested the filesystem signal directly, after this essay first filed. Reproduced
independently for this amendment, correcting the seeding artifact the first attempt hit (a
hand-written seed file is not byte-identical to `_dump()`'s own formatting, so its first
cycle is not a true no-op; the test below seeds by running `cycle` once, then measures a
*second* call against that canonical baseline):

```
$ md5sum state.json; stat -c '%Y' state.json
<hash-A> <mtime-A>
$ sleep 2 && python3 write_runtime_state.py --state-file state.json cycle --phase 2 \
    --phase-source roadmap.md --work W37 --work-source roadmap.md --slice W37-4 \
    --slice-source roadmap.md
runtime state unchanged: state.json
$ md5sum state.json; stat -c '%Y' state.json
<hash-A> <mtime-A>          # identical to both, including mtime
```

**Content unchanged (confirms Ruling 47(d) holds) and mtime unchanged too** — the file is
not touched at the OS level at all on a no-op cycle, which is the direct, unsurprising
consequence of the code's own write guard (`cycle`, read again for this amendment):

```python
new_bytes = _dump(doc)
old_bytes = path.read_text(encoding="utf-8") if path.exists() else None
if new_bytes != old_bytes:
    path.write_text(new_bytes, encoding="utf-8")   # only path that can move mtime
    print(f"runtime state written: {path} ...")
else:
    print(f"runtime state unchanged: {path}")        # path.write_text is never reached
```

`path.write_text` — the only statement that could advance the file's mtime — sits inside
the branch that a genuine no-op never enters. **So the gap is not "the JSON does not record
when it was checked"; it is "nothing available on this file, at any layer, records it."** A
stopped writer and a running one that finds nothing to do are indistinguishable by content,
by mtime, or by anything else this artifact carries.

**Why this is worth filing rather than a curiosity: mtime is this repository's own
established liveness idiom, and for this artifact it silently does not work.**
`docs/process/delivery-process.md:253` names *"mtime staleness checks"* as one of the
watcher's own mechanical duties, and F67 (`docs/audit/findings/F67.md`) — the hygiene
monitor that died on its first clean sample — records the general practice directly:
*"`ps -p <pid>` and the state file's mtime are the adopted liveness proxies, judged stronger
than a heartbeat line."* Applying that same, already-adopted technique to
`runtime-state.json` gives a wrong answer, silently — worse than having no technique,
because a reader has no reason to distrust it here specifically.

**A `checked_at` field inside the JSON is ruled out, not merely undesirable — this is the
fix everyone will reach for first, including this essay's own first draft.** Read at its
primary source, not only at the closure record's paraphrase: `docs/plans/2026-08-30-
nt-0014-q1-q3-q4-rulings.md`, Ruling 47(d), *"The acceptance test, stated as the violation
that must become impossible"*: *"Slice E is not accepted until a test shows that **a B
written by a watcher cycle in which nothing changed is byte-identical to the previous
one.** If any byte moves, a freshness token is refreshing while its content is frozen, and
**that is F31 regardless of what the surrounding prose says.**"* A `checked_at` timestamp
refreshed every cycle is precisely a freshness token refreshing while the surrounding
content is frozen — the ruling does not leave room for a justification. The existing test
that enforces this, read for this amendment rather than assumed to cover only content:
`tests/test_watcher_runtime_state.py::test_a_cycle_with_no_change_is_byte_identical`
asserts `second_bytes == first_bytes` only — it does not read or assert anything about
mtime, confirmed by reading the test body directly. Any fix must not break this test; a
fix that only touches mtime cannot, since the test never looks at mtime.

**Two candidate mechanisms, named without ranking — the choice belongs to whoever builds
it, not to this essay:**

- `os.utime()` the file on every `cycle` call, unconditionally. Advances mtime without
  touching a single content byte, restoring the repository's own established idiom for
  this one artifact, and does not conflict with the existing byte-identity test (confirmed
  above).
- A separate sidecar file (e.g. `.last_cycle`) carrying only a timestamp, written every
  cycle, leaving `runtime-state.json` itself untouched and Ruling 47(d)'s test exactly as
  it stands.

## Shared shape with F69

F69 (`write_runtime_state.py cycle` cannot clear a field — "no active slice" is
inexpressible): the position block's schema has no way to express "no active slice,"
because `_position_block_content` only overwrites a field when a value is supplied. F72
(this row): the schema has no way to express "checked and unchanged" separately from "not
checked recently," because `written_at` is the only per-block timestamp and it moves on
content change alone. Different fields, same mechanism-level shape — **the state model is
narrower than what its own consumers (a person reading the file, or a future automated
staleness check) need to ask of it.** One instance is an anecdote; two are a shape worth
naming together, per the watcher's and lead's own framing, verified against F69's actual
filed text rather than assumed to match.

## Mutation that must become detectable

Stop the writer process entirely. The artifact left behind is **byte-identical, mtime
included** (confirmed above), to a healthy writer's output from a cycle that re-derived its
inputs and found nothing changed — there is no reachable state today, on this file alone,
by any available signal, that distinguishes "the watcher is dead" from "the watcher is
alive and idle." `written_at` answers "when did content last change," never "was this
process alive as of now," and neither does anything else about the file.

## Scope of this finding

- **Not a defect in `write_runtime_state.py`, `cycle`, or `watcher.md`.** All three are
  internally consistent with each other and with Ruling 47(d); nothing here asks for any of
  them to change their current behaviour.
- **Not fix-before-close.** F58 already carries the "no live process invokes the script on
  a schedule" gap as its own open row; this finding is about what the artifact could not
  tell a reader even if a live process were invoked reliably every cycle.
- **Proposed disposition** (a proposal; the verdict is the lead's), **amended 2026-09-02
  — the fix asked for is a property, not a field.** This essay's own first draft proposed a
  `checked_at`/`derived_at` JSON field; that proposal is withdrawn and ruled out, not
  merely revised, per Ruling 47(d) read at its primary source above — a field that refreshes
  every cycle inside the state file is a freshness token moving while content is frozen,
  which the ruling names as F31's shape "regardless of what the surrounding prose says." No
  field added to `runtime-state.json` itself can satisfy this finding without violating that
  ruling. **Carry forward, unowned, asking for**: a no-op cycle observable — by mtime, by a
  sidecar, by any means outside the state file's own bytes — without changing the state
  file's bytes. Two candidate mechanisms are named above (`os.utime()`; a separate sidecar
  timestamp file) without ranking one over the other; whoever builds this chooses. Whichever
  is chosen must leave `tests/test_watcher_runtime_state.py::
  test_a_cycle_with_no_change_is_byte_identical` passing unmodified — confirmed above that
  neither candidate touches what that test reads. Sizing and ownership are not decided here.
