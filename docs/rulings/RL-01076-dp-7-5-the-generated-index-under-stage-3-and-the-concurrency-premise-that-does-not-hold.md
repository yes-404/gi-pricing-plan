# RL-1076 — DP-7-5: the generated index under Stage 3, and the concurrency premise that does not hold

## Verified first, at 7d5d6e0a3730bfd790dace3a95c63a0ea71ec031

This rules `PL-1070`'s **DP-7-5** (`PL-1070-…-leaf-plan.md:334`, referenced again at `:982`,
`:1006` and `:1128`). Its own `Resolved by` cell names *"The lead, before the first Stage 3
executor is spawned"*, and its `Kind` cell says *"it is the lead's, not this plan's"*. **The
lead delegated it to this role in writing on 2026-09-19**; that is the lead's to delegate and
is recorded here so the authority chain is legible rather than assumed. Read at `7d5d6e0`,
worktree `agent-a7575676d7fdc9dcf`, `git status --short` empty at the ruling's base.

**The decision point as it was put**, quoted from `:334`:

> `docs/INDEX.md` is regenerated by `scripts/doc-index.py` and W37-7, W37-8, W37-9 and W37-10
> may run beside each other (`PL-939:379-382`). Four concurrent branches each regenerating one
> generated file is a guaranteed conflict | (a) each slice regenerates `docs/INDEX.md` in its
> own final commit and resolves conflicts by **regenerating, never by hand-merging**; (b) no
> slice touches `docs/INDEX.md` and W37-11 regenerates it once; (c) serialise the four slices
> | **(a)** …

**1. The premise is false. The four slices may not run beside each other.**
`docs/process/delivery-process.md` §8 (heading at `:150`), quoted from `:152`: *"Sequential
processing of a layer's **children** (Project→Phase→Work→Slice: **no two Slices run at once,
at any layer**)"*. And the clause that forecloses the obvious rebuttal, same section, `:161`:

> **The interest §8 protects is resource contention, not plan stability.** Two children can be
> perfectly plan-independent and running them concurrently still breaches this rule, so an
> exception argued on plan-independence argues past it (`RL-871` refused exactly that
> argument).

**2. What `PL-939:379-382` actually says, and why it does not override §8.** The column the
DP cites is headed **"May run beside"** (`PL-939:371`), and W37-7's row lists `W37-8, W37-9,
W37-10`. So the plan does assert the permission — it is not merely recording independence.
But **`PL-939` declares exactly two departures from §8 and neither covers Stage 3.**
*Departure 1* (heading line `:385`) authorises the **S1** fan-out, in terms — *"They may
therefore be dispatched together"* — for W37-1, W37-2 and W37-3, on availability grounds.
*Departure 2* (heading line `:393`) is about DP-1 moving seven skills into W37-6's commit, a
scope change, not a concurrency one. There is no third: the next paragraph, `:398`, is
*"What must not be fanned out"*, which narrows rather than widens. **A permission §8 denies
by default, asserted in a table cell with no declared departure, does not carry.** The S3
slices run one at a time.

**3. The plan's stated reason for refusing (b) is independently correct, and I verified it
by hitting it.** Filing `RL-1075` on this branch without regenerating the index turned
`audit-docs.py` check 32 red — `check 32: docs/rulings/RL-01075-….md:2: RL-1075 does not
resolve in docs/INDEX.md` — and `doc-index.py --check` red with it; both returned to exit 0
only after `python3 scripts/doc-index.py`. So (b) — no slice touches the index, W37-11
regenerates once — **leaves the gate red on every intermediate merge for the whole of Stage
3**, exactly as the plan says. Measured, not reasoned.

**4. But a conflict is still reachable under sequential execution**, which is why this does
not simply dissolve. `docs/INDEX.md` is generated from the whole corpus, so any two branches
that each add a governed record write different rows into the same table region. Sequential
*execution* does not imply sequential *branch lifetime*: a slice branched before the previous
slice merged must rebase across that merge, and the index conflicts on the rebase. The
mechanism DP-7-5 asks for is therefore still needed — for one branch rebasing, not for four
branches racing.

## Ruled

**(a) is adopted. (b) is refused. (c) is struck from the option set, because it is not a
choice available to this plan.**

**(i) Each slice regenerates `docs/INDEX.md` in its own final commit**, by running
`python3 scripts/doc-index.py` and committing the result, and verifies with
`python3 scripts/doc-index.py --check`.

**(ii) A conflict in `docs/INDEX.md` is resolved by regenerating, never by hand-merging or
by choosing a side.** On any conflict: take either side to clear it, re-run
`scripts/doc-index.py`, and commit the regenerated file. The generated artifact's only
correct content is what its generator produces from the merged corpus; a hand-resolved
generated file is a file that matches neither branch's source. This is `CLAUDE.md` §2's
*"`docs/contracts/` is generated and never hand-edited"* applied to the other generated
artifact, as the plan's recommendation already argued.

**(iii) Each Stage 3 PR body states rule (ii)**, as the plan proposes. Kept.

**(iv) (c) is not an option, because the slices are already serialised.** `PL-1070` lists
*"serialise the four slices"* as something this decision point could choose. It cannot:
`delivery-process.md` §8 has already decided it, for an interest — resource contention —
that a plan's convenience does not reach. Listing it as an option misreads a standing
process rule as discretionary. **Stage 3's slices run one at a time whatever this ruling
says**, and nothing in Stage 3 may be planned or dispatched on the contrary assumption.

**(v) The rationale is corrected even though the recommendation is adopted.** DP-7-5's
grounds — *"Four concurrent branches each hand-resolving a generated file"* — describe a
situation the process forbids. The rule survives on the rebase ground in §4 above. This
matters because a rule kept for a reason that is not true is a rule that gets dropped the
moment someone checks the reason: `PL-1070:1128`'s risk paragraph 3 should be read as
describing rebase conflicts across sequential merges, not concurrent execution.

## What it obliges

- **Each Stage 3 executor** (W37-7 first, then W37-8, W37-9, W37-10, one at a time): applies
  (i)–(iii). `PL-1070`'s Task 14 Step 3 and `:1006` already state the mechanism and need no
  change; only their stated reason is corrected by (v).
- **The lead**: writes `RL-1076` into DP-7-5's `Resolved by` cell. As with `RL-1075`, the
  plan edit is the lead's, not this role's (`docs/process/document-ids.md:152`).
- **A disclosure for the lead and the planner, which this ruling does not itself dispose
  of.** `PL-939`'s **"May run beside"** cells for W37-7, W37-8, W37-9 and W37-10
  (`PL-939:379-382`) **assert a permission `delivery-process.md` §8 denies, with no declared
  departure covering Stage 3.** The plan knows how to declare one — it does so twice — so the
  omission is a defect in the plan, not an implied exception. Two dispositions are available
  and the choice is not mine: strike or reword those four cells to state plan-independence
  rather than permission, **or** have the planner seek a third departure on the record and
  the maintainer rule it. **Until one of those happens the default binds and the slices run
  sequentially.** Filing this as a finding with an owner is the lead's.
- **This ruling deliberately does not decide**: whether Stage 3's slices should be permitted
  to run concurrently (that is a departure from a process spec — `CLAUDE.md` §0 routes it to
  a spec change with the maintainer's acceptance, and `RL-871` is the precedent against the
  argument most likely to be offered); nor anything about `docs/INDEX.md`'s generator itself.

## Acceptance — the violation that must become detectable

**The violation: `docs/INDEX.md` lands in a commit as something other than what
`scripts/doc-index.py` produces from that commit's corpus.** A hand-resolved generated file
is indistinguishable from a correct one by inspection, which is why this needs a check rather
than a convention.

- **`python3 scripts/doc-index.py --check` is the check, and it already exists and already
  reds.** *Violation: any edit to `docs/INDEX.md` that the generator would not produce —
  delete a row, reorder two rows, or hand-add a row for an id with no file, then run it.* I
  showed it red on real broken input in the course of this ruling: with `RL-1075` filed and
  the index not regenerated, `doc-index.py --check` failed and `audit-docs.py` check 32
  printed `RL-1075 does not resolve in docs/INDEX.md`; both returned to exit 0 after
  regeneration. That is the check firing on the exact defect class (ii) forbids, observed
  rather than asserted.

- **What is *not* yet checkable, stated rather than papered over.** Nothing mechanically
  detects a *hand-merged* index that happens to be byte-identical to the generated one —
  and nothing needs to, because in that case the artifact is correct and only the method was
  wrong. Conversely, no check enforces that a slice regenerated *in its own final commit*
  rather than earlier; `--check` at the PR's tip is what CI sees, and that is the property
  that matters. **This ruling adds no new check**, because the one the rule needs is already
  in the gate and already proven red. Adding a second instrument over the same property
  would be the duplicated-status shape `RFC-756` names.

- **The §8 conflict in §"What it obliges" carries no check and is not given a forced one.**
  It is a disclosure for the lead about a plan's table cells; the rule it breaches lives in a
  process document and is enforced by how the team dispatches work, not by a script.
