# Open Questions

Unresolved design questions. Every question is mirrored from the §10 "Open questions"
section of the spec that raised it. **Phase 0 exit requires this file to be empty or
every remaining entry explicitly marked `deferred` with a target phase.**

**Status values:** `open` · `decided` (link the ADR) · `deferred` (state the phase) ·
`dropped` (state why).

**2026-08-14 — Track A research closed one question and sharpened two others.** OQ-RATE-1 is
`decided`; OQ-MODEL-1 and OQ-RATE-2 carry new evidence. See
[`research/track-a-findings.md`](research/track-a-findings.md).

**How to close one:** if the decision constrains more than one module or is expensive to
reverse, write an ADR and set status `decided → ADR-NNNN`. Otherwise record the decision
inline in the owning spec and set status `decided (in spec)`. Never delete a row.

## DATA — data management ([`01-data-management.md`](specs/01-data-management.md))

| ID | Question | Options / trade-offs | Recommendation | Owner | Status |
|---|---|---|---|---|---|
| **OQ-DATA-1** | ~~Large-loss handling: preparation step or modelling decision?~~ **DECIDED 2026-08-14: modelling decision, applied at fit time.** | Delegated to Claude. Datasets are immutable versioned artifacts, so baking a cap in means a new Dataset Version — plus re-validation and re-profiling — for every capping assumption. Datasets stay assumption-free and one validated dataset serves many capping assumptions. The reconciliation objection is answered rather than dismissed: `FR-MODEL-74` requires the Peril Structure to reconcile *after* restoration against uncapped observed data, and the dossier to state the treatment — otherwise a capped model looks like a modelling error. | Claude | **decided** |
| **OQ-DATA-2** | ~~Incremental/append ingestion, or full snapshot per version?~~ **DECIDED 2026-08-14: full snapshots for Phase 1; append deferred to Phase 2 under a stated constraint.** | Delegated to Claude. Phase 1a's demo dataset is freMTPL2 — small enough that snapshots are free. Append would add real complexity now (validation must reason about which parts are new; profiling and PSI would need incremental variants) to solve a problem the project does not yet have. | **Full snapshots**, per `FR-DATA-2` as already written — no spec change needed, which is itself a point in favour. Append is **not** ruled out: `FR-DATA-40` records the constraint any future append mode must meet — it must still materialise a complete, content-addressed, independently validatable version, so FR-OVR-1 immutability holds and only the *cost* changes. Content-addressing (ID-4) already deduplicates unchanged parquet parts, so most of the saving is available without an append mode at all. | Claude | **decided** |
| **OQ-DATA-3** | ~~Keep the `sql` custom validation check? If so, what control?~~ **DECIDED 2026-08-14: keep it, Admin-authored, single Approver, behind a workspace feature flag defaulting to off. Revisit after Phase 1.** | Keep + dual approval: maximum expressiveness, real sandboxing burden (NFR-DATA-9). Keep + admin-only: less flexible but far fewer reviewers to train. Drop: the declarative checks cover ~95 % of real rules; the last 5 % becomes a feature request. | **Maintainer accepted the recommendation.** The control that matters is how few people can *author* one, not how many must approve it — dual approval on a check nobody may write anyway adds ceremony without adding a decision, and ceremony is what turns review into signature. The flag (`features.sql_validation_check_enabled`, `07` FR-PLAT-46, already shipped in W2 defaulting to off) means a workspace that never needs the escape hatch never carries its risk. Sandboxing is unchanged: a single `SELECT`, a read-only DuckDB connection with no filesystem or extension access, and a hard time budget. Applied to `01` §4.5, which previously required two approvers. **Revisit after Phase 1** with evidence of what it was used for; if the declarative checks could have expressed all of it, remove it. | maintainer | **decided** |
| **OQ-DATA-4** | ~~Where do IBNR / claims-development adjustments live?~~ **DECIDED 2026-08-14: out of scope — the platform consumes developed data supplied by the user, and warns about immature periods.** | Preparation step (developed amounts in the dataset), modelling offset, or out of scope (user supplies developed data). Currently only `VR-ACT-14` warns about immature periods. | **Maintainer decided: out of scope.** Claims development is an actuarial exercise with its own methods, judgement and review, and a pricing platform that half-performed it would produce developed amounts nobody had signed off. The user supplies developed data; `VR-ACT-14` remains the platform's only treatment, warning that the most recent months are immature so that fitting on them is a visible choice rather than an accident. *Not adopted from the recommendation:* a first-class `development` preparation step in Phase 4. If the monitoring work later needs triangles, that is a new question rather than a deferred half of this one. | maintainer | **decided** |
| **OQ-DATA-5** | ~~Ship ONS/ABI reference data, or only loaders?~~ **DECIDED 2026-08-14: loaders for every source; ship data only where the licence is unambiguously permissive. Never ship ABI group tables.** | Shipping is far better UX but the licences (ONS OGL is permissive; ABI vehicle groups are **not** freely redistributable) differ per source and get us wrong quickly. | **Maintainer accepted the recommendation.** Every source gets a loader and a documented fetch step, so a workspace can always obtain the data itself. Actual rows ship only where the licence is unambiguous — ONS NSPL and the bank-holiday calendar under OGL. **ABI vehicle group tables are never shipped**: they are not freely redistributable, and shipping them would put a licence breach in every clone of the repository. | **OQ-DATA-6** | ~~Acknowledgement granularity — per rule per report, or a time-boxed standing acknowledgement?~~ **DECIDED 2026-08-14: per report, as FR-DATA-18 already specifies, plus a carry-forward affordance that still requires an explicit act.** | Per report (FR-DATA-18): strongest evidence trail, but a known seasonal warning is re-justified every month, breeding rubber-stamping. Standing: less fatigue, weaker evidence, risk of a stale acknowledgement hiding a real change. | **Maintainer accepted the recommendation.** FR-DATA-18 stands unchanged: an acknowledgement is scoped to `(dataset_version_id, rule_id, report_id)` and does not carry forward. Fatigue is a UI problem and a standing acknowledgement is a governance one; a stale standing acknowledgement hiding a real change is the failure this avoids. | maintainer | **decided** |

## MODEL — modelling ([`02-modelling.md`](specs/02-modelling.md))

| ID | Question | Options / trade-offs | Recommendation | Owner | Status |
|---|---|---|---|---|---|
| **OQ-MODEL-1** | Ship `expression` custom objectives in Phase 1, or templates only? | Templates only: the §4.5 catalogue already covers Tweedie tuning, capping, and asymmetric losses — i.e. most of the stated need — with zero parser/sandbox risk. Expressions in Phase 1: the headline differentiator lands early, but the AST parser, SymPy derivation, and certification are all new and all security-relevant at once. | Ship templates in Phase 1 and expressions in Phase 2, but **specify and build the certification machinery in Phase 1** for templates too (it is the same checks). That way expressions arrive as a new front-end onto proven machinery rather than a new subsystem. | maintainer | open |
| **OQ-MODEL-2** | GBM prediction intervals — how? | Paired quantile models: honest, 2–3× fit cost, and the quantiles can cross. Variance-model approximation: cheap, easy to misread as a genuine predictive interval. `uncertainty: unavailable`: honest and free, but violates the spirit of R5 for GBMs specifically. | Default to `uncertainty: unavailable` with an explicit reason string, and offer opt-in paired quantile models as a separate Model in the same family. Never ship the variance approximation — a wrong interval on a price is worse than no interval. | maintainer | open |
| **OQ-MODEL-3** | Can a Rating Version rate on the GLM approximation instead of calling the GBM? | Rate on the approximation: fully tabular, inspectable, fast, and it is what most insurers actually deploy — but the deployed prices are then *not* the model that was validated. Call the GBM: exact, but the rating structure contains a black box on the p99 latency path. | Support both, as an explicit, recorded choice on the Rating Version (`model_reference_mode: exact | approximation`), with the approximation's fidelity statement (FR-MODEL-36) surfaced at approval and the residual error carried into the dislocation report. Forcing one choice would make the platform unusable for one of two large user groups. | maintainer | open |
| **OQ-MODEL-4** | Auto-detect interaction candidates from SHAP interaction values? | Auto-detection surfaces genuine structure an actuary would miss, and is a well-worn path to overfitting and to rating structures nobody can defend. | Surface them as *suggestions* in the factor workbench with their exposure share and holdout lift, never auto-add. Any interaction entering a Model Spec must be an explicit Factor with a rationale (FR-MODEL-1). | maintainer | open |
| **OQ-MODEL-5** | Which credibility standard for `credibility_weighted` grouping? | Limited fluctuation (classical): simple, familiar to UK GI actuaries, one parameter (standard for full credibility), theoretically weak. Bühlmann–Straub: defensible, handles heterogeneous exposure properly, needs variance components that are awkward to estimate on thin cells and harder to explain in a model document. | Implement limited fluctuation as the default (it is what reviewers expect to see), with Bühlmann–Straub as a selectable method whose variance-component estimates are persisted in the grouping evidence. Record the choice per grouping — it is a modelling judgement, not a platform constant. | maintainer | open |
| **OQ-MODEL-6** | Hard gate on factor count / exposure-per-parameter, or diagnostic warning only? | Hard gate: prevents a class of overfitted models reaching approval, and will block legitimate large models on large books. Warning: relies on the Approver noticing. | Warning by default, with a **workspace-configurable** hard threshold that defaults to off. Governance belongs in approval (`06`), not in an arbitrary platform constant. | maintainer | open |
| **OQ-MODEL-7** | How are protected-characteristic proxies detected, and what happens when detection fires? | Needs (a) a statistical test — e.g. mutual information or AUC of the factor predicting a protected characteristic on a reference population — and (b) a policy. We do not hold protected characteristics, so any test needs an external reference dataset the insurer supplies. | Phase 0: specify the `prohibited` flag (FR-MODEL-5) and stop there. Phase 3: add an optional "proxy assessment" that consumes an insurer-supplied reference table and produces evidence attached to the approval request — never an automated block, because the judgement is legal, not statistical. Track as a Phase 3 deliverable. | maintainer | deferred (Phase 3) |

## OPT — optimisation ([`04-optimisation.md`](specs/04-optimisation.md))

| ID | Question | Options / trade-offs | Recommendation | Owner | Status |
|---|---|---|---|---|---|
| **OQ-OPT-1** | Which solver family? | SLSQP (`scipy`): simple, no extra dependency, adequate for a few hundred smooth segment factors, degrades badly at thousands of variables and with non-smooth constraints. `cvxpy` + a conic solver: far more robust, gives genuine infeasibility certificates and shadow prices for free (FR-OPT-12), but constrains objectives to convex forms — which excludes some blends users will want. | Start with SLSQP in Phase 4 for the segment-factor formulation, and specify the constraint set so that a convex reformulation stays available. Revisit with `cvxpy` if segment counts exceed ~1 000 or infeasibility diagnosis (NFR-OPT-4) proves unreliable. | maintainer | deferred (Phase 4) |
| **OQ-OPT-2** | Competitor position: first-class concept or just a dataset column? | First-class: enables market-response modelling, needs a competitor data model, ingestion cadence, and matching logic we cannot validate without the data. Column: zero platform cost, user does the joining, but then "rank in market" cannot be a constraint or a monitored metric. | Dataset column in Phases 1–4, with the *convention* documented (column naming, semantic type `competitive_position`) so it can be promoted to first-class later without a migration. | maintainer | open |
| **OQ-OPT-3** | Expected claims in the profit objective — platform models or externally supplied? | Platform models: internally consistent, everything traces to an approved artifact. External (reserving-derived): matches what the finance function believes, and will differ from our models in ways that get noticed in a pricing committee. | Support both: the profit definition (FR-OPT-9) names its expected-claims source, which may be a Peril Structure or a supplied column on the portfolio dataset. Force the choice to be explicit rather than picking a default that silently disagrees with finance. | maintainer | open |
| **OQ-OPT-4** | How is demand-model endogeneity handled? | Historic prices were set by a structure already conditioned on risk, so naive elasticity is biased toward zero (or worse). Options: instrumental variables (needs a valid instrument, rarely available), randomised price testing (see OQ-OPT-5), or documenting the caveat. | Document prominently and *quantify*: FR-OPT-2's price-variation report is the honest surface for it. Specify an `identification_note` field on every Demand Model that is required before it can be used in optimisation. Real identification needs OQ-OPT-5. | maintainer | open |
| **OQ-OPT-5** | Should the platform support randomised **price testing** on live traffic? | It is the only clean answer to OQ-OPT-4, and it means deliberately quoting some customers a different price to learn from it — operationally involved and ethically loaded, with FCA fair-value implications. | Do not build it in Phases 1–4. | **OQ-OPT-6** | ~~GIPP: what is the correct ENBP when channels differ?~~ **RESOLVED 2026-08-14.** | Not a judgement call — **the rule prescribes it.** ICOBS 6B.2.5R(1) requires the channel the customer used when they **first purchased** the policy; 6B.2.5R(2) falls back to the channel most commonly used by new-business customers where the original is unavailable or unidentifiable. | **Decided: follow the rule.** This corrected a real design defect — the spec and the `GippCheck` contract keyed ENBP off the *renewal* channel, which diverges from the rule for precisely the customers it targets: those who switched channel between purchase and renewal. Now FR-OPT-18/29, with the fallback share reported as a data-quality signal. My earlier recommendation ("same-channel with an explicit mapping") was close but wrong on which channel. | maintainer | **decided (in spec)** |

## GOV — governance ([`06-governance.md`](specs/06-governance.md))

| ID | Question | Options / trade-offs | Recommendation | Owner | Status |
|---|---|---|---|---|---|
| **OQ-GOV-1** | Audit hash chain: per workspace or global, and is a self-held chain enough? | A chain the platform operator controls end to end detects *storage-layer* tampering but not a determined operator who can recompute it. ## PLAT — platform ([`07-platform.md`](specs/07-platform.md))

| ID | Question | Options / trade-offs | Recommendation | Owner | Status |
