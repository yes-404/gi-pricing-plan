# Contributing

This project has two people: the maintainer, who also works as core team and
contributor, and the collaborator, who works as core team and contributor and holds collaborator
access. Later outside contributors work from forks. Read [`CLAUDE.md`](CLAUDE.md) first:
it holds the rules that bind every session, and this file does not restate them.

## How work is organised

- A **milestone** is a version (for example `v0.3.0`) holding the Works planned for it. The maintainer decides which Works belong to it.
- A **Work** is one issue, made with the Work form. It is the smallest unit a contributor
  delivers. A single slice is not accepted as a Work.
- Other issues: a **finding** (something is wrong), a **decision** (a choice the
  specification leaves open) and the pinned **coordination** issue for anything that crosses
  Works. Labels are listed in the repository's label set; the maintainer sets the milestone
  and the severity at triage.
- Project records that stay as files: specifications, workflows, contracts, decision
  records in [`docs/adrs/`](docs/adrs/), acceptance lines, the requirement-to-test trace
  and the process rules. Everything else is on GitHub.

## Before you start

1. Pick a Work the maintainer has accepted, and be assigned to it.
2. Post your plan as a comment on the Work issue. Write no code until the maintainer
   replies `Plan accepted`.
3. A change to an accepted plan is an edit to the Work issue, with the contributor's
   acknowledgement. The reviewer checks each condition against the branch by name.
4. Response times: the plan and the first review of a pull request within three working
   days; a question within two.

## Set up

You need Python 3.12, [`uv`](https://docs.astral.sh/uv/), Node 22 or later, `pnpm` and Docker.
Fork the repository (outside contributors) or branch from `main` (collaborators).

```bash
uv sync --all-packages --dev
pnpm --dir frontend install --frozen-lockfile
docker compose -f deploy/docker-compose.yml up -d    # postgres, redis, minio
```

`--all-packages` is not optional. Backend tests need a test database of their own through
`GIP_TEST_DATABASE_URL`. The commands and every setup trap are in
[`.claude/skills/dev-commands/SKILL.md`](.claude/skills/dev-commands/SKILL.md).
Use public or synthetic data only (freMTPL2). Never use real policy, claims or exposure data.

## Making a change

- Branch from `main`. Keep the branch short-lived.
- **Spec before code.** Read the specification for the area first. A capability not yet
  specified needs a spec change first: follow `.claude/skills/spec-change`.
- Write the test with the code, and see it fail before the code makes it pass.
- Never edit by hand: `docs/contracts/` (generated by
  `uv run python scripts/generate-contracts.py`) and `frontend/src/api/generated`.
- Stay inside the Work issue's permitted paths. A change outside them needs a comment on
  the Work issue first.
- If the Work needs a new dependency, open a decision-needed issue first. A migration is
  announced on the coordination issue.
- New requirement ids and decision numbers are assigned by the core lead at the merge turn.
  Write placeholders until then.

## The gate

Run both halves before you push. A Python-only run has been green while the frontend was
red. Read each command's own exit code: `cmd | tail -1 && echo ok` reports the exit code of
`tail`.

```bash
uv run ruff check . && uv run mypy && uv run lint-imports && uv run pytest -q
python3 scripts/audit-docs.py && uv run python scripts/req-coverage.py
uv run python scripts/generate-contracts.py --check
pnpm --dir frontend install --frozen-lockfile && pnpm --dir frontend generate:api
pnpm --dir frontend lint && pnpm --dir frontend type-check
pnpm --dir frontend test && pnpm --dir frontend build
```

## Pull requests

- **One Work is one pull request**, built as a series of commits, one per slice. Each
  commit carries its spec change, code and tests, passes the gate on its own, and is
  reviewed on its own. Fold a fix into the commit it belongs to.
- The title is a Conventional Commit line. Add one type label. Fill in the template: the
  commit table, the gate evidence (range `origin/main...<branch>`), the changelog line,
  the decisions reached, and the AI disclosure.
- **Squash at merge.** One Work is one commit on `main` that lists its slices; the reviewed
  series stays in the pull request. This is revisited after the first two contributor Works.
- The squash commit keeps the contributor as author and the changelog names them.
- The one-pull-request rule binds contributors only. The core team follows the series form
  by default and may merge a single slice for an urgent correctness fix, shared files that
  several Works wait on, or external timing. Every core merge still passes the required
  checks, the independent audit and its review tier.
- Every contributor Work gets an independent audit against the specification before merge,
  with failing-first evidence per commit.
- **Nobody merges their own pull request.** The collaborator may merge after approving. The core
  lead merges one pull request at a time.
- The first Work of a new contributor is a trial, reviewed afterwards.

## Review

Review is by risk, in four tiers:

1. **Always:** required CI. No direct push to `main`.
2. **Every contributor pull request:** the maintainer approves.
3. **High-risk areas:** the other person cross-reviews. A reviewer is requested through
   `.github/CODEOWNERS`; the core lead applies the `high-risk` label. If the cross-review
   does not happen within **three working days**, the maintainer may proceed.
4. **The rest of the core team's work:** an independent audit.

The six high-risk areas:

- the rating and scoring path;
- money handling;
- the shared data contracts (`packages/model-schema/`, `docs/contracts/`);
- authentication and roles;
- database migrations;
- the project's own rules and CI (`CLAUDE.md`, `CONTRIBUTING.md`, `SECURITY.md`, `.github/`).

The paths for each area are in `.github/CODEOWNERS`.

## Decisions

A choice that binds the product is written as a decision record in
[`docs/adrs/`](docs/adrs/), by the pull request that enacts it. Open a decision-needed
issue first; the maintainer closes it with a comment starting `Decided:` and the date. A
decision reached in an issue is listed in the pull request's Decisions section. A record is
numbered, and superseded, never edited. The shape is `docs/_templates/ADR.md`.

## Findings

Findings are public by default: open an issue with the finding form. A defect that could
mean a **wrong price**, a **data leak** or a **security defect** is not filed publicly.
Report it as a private advisory, as [`SECURITY.md`](SECURITY.md) says. The other person is
added. It is probed first. A refuted report is closed with a short public note. A confirmed
one stays private until the fix merges, then becomes a public issue and a changelog entry.
A severity is set by a probe, not by words. Open findings with no owner or milestone are
posted weekly to the coordination issue.

## Use of AI

AI tools and agent teams are welcome on four conditions.

1. **Disclose it.** Every pull request names the tools and model versions, and what they
   did. AI-written commits carry a `Co-Authored-By:` trailer.
2. **A named person is accountable.** That person has read every line, can explain it
   without the tool, and answers review.
3. **Agents act under a named person.** An agent opens pull requests and comments only
   under a named person's account.
4. **Same bar.** AI-assisted work meets the same tests, review and cross-review.
   Undisclosed AI use is grounds to close a pull request.

No session links, credentials or real policy and claims data in any issue, comment or commit.
Each team pays its own AI and machine costs.

## Stale work

No update on a Work for 14 days: the maintainer marks it `stale` at the weekly review.
After 7 more days it may be reassigned. Applied by hand; there is no workflow for it.

## Pausing or leaving

Push your branch, say so on the Work issue, and the Work is reassigned.
